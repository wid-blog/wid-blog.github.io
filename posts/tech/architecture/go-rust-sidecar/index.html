Go 서비스 옆에 Rust 사이드카를 두는 이유

p50 은 넉넉한데 p99 가 응답 상한을 넘는 서비스가 있다. 검색 랭킹, 추천 서빙처럼 정해진 시간 안에 답해야 하는 서비스에서 늦은 응답은 틀린 답이 아니라 없는 답이다. 이런 서비스에서 요청 처리는 Go 로 하고, 모델 추론이나 대용량 조회 테이블은 같은 Pod 의 Rust 프로세스에 맡기는 구조가 쓰인다.

이 구조는 지연 예산에서 출발한다. 포인터가 많은 장수명 데이터를 Go 힙에서 분리하면 가비지 컬렉터(GC) 비용이 줄어든다. 분리한 연산을 같은 배포 단위에 두면 네트워크 왕복이 생기지 않는다. 사이드카는 두 조건을 함께 만족한다.

꼬리 지연#

응답 상한이 있으면 평균보다 꼬리 지연(Tail Latency)이 중요하다. p99 가 상한을 넘으면 100건 중 1건은 응답하지 못한다. 평균 지표로는 정상으로 보이는 서비스가 일정 비율의 요청을 계속 놓친다.

꼬리 지연의 원인은 주로 네트워크 왕복, 락 경합, 디스크 I/O, GC 다. 이 중 언어 런타임의 영향이 가장 큰 것이 GC 다.

Go GC 와 장수명 데이터#

Go GC 는 대부분의 작업을 애플리케이션과 동시에 수행한다. 전역 일시정지(Stop-the-World)는 mark 단계의 시작과 끝에 짧게 일어난다. Go GC 가이드(Go 1.19 기준)에 따르면 이 일시정지는 힙 크기에 비례하지 않도록 설계됐다. 일시정지 자체가 길어지는 경우는 드물다.

비용은 GC 의 작업량에서 생긴다. 가이드는 GC 의 CPU 비용이 살아 있는 힙(Live Heap) 크기에 비례하고, 포인터가 많을수록 GC 가 방문할 대상이 늘어난다고 설명한다. 지연의 원인으로는 다음을 든다.

  • mark 단계 동안 GC 가 CPU 의 25% 를 목표로 사용해 goroutine 스케줄링이 늦어진다
  • 할당 속도가 빠르면 요청을 처리하던 goroutine 이 GC 작업을 함께 수행한다(Mutator Assist)
  • mark 단계 동안 포인터 쓰기에 추가 작업이 붙는다
  • root 스캔을 위해 실행 중인 goroutine 을 잠시 멈춘다

Go GC 는 세대 구분이 없다. 문자열 키의 map, 포인터로 연결된 피처 테이블, 객체 그래프 형태의 캐시처럼 포인터가 많은 장수명 데이터를 힙에 두면, GC 주기마다 그 데이터를 다시 순회한다. 포인터가 없는 큰 배열은 스캔할 내용이 없어 부담이 작다. 모델 가중치도 대부분 포인터 없는 텐서라 GC 부담이 작다. 추론을 사이드카로 분리하는 이유는 GC 가 아니라 추론 엔진의 생태계와 장애 격리다. 요청 처리 코드는 객체가 짧게 살고 금방 사라지는데, 같은 힙에 포인터가 많은 장수명 데이터가 섞이면 그 순회 비용을 요청 처리가 함께 부담한다.

GC 진단#

구조를 바꾸기 전에 GC 가 실제 원인인지 확인한다. GODEBUG=gctrace=1 은 GC 주기마다 걸린 시간과 힙 크기를 출력한다. runtime/metrics 는 GC 일시정지 분포와 GC 가 사용한 CPU 비중을 지표로 제공한다. p99 가 튀는 시점과 GC 주기가 겹치는지, GC 의 CPU 비중이 높은지를 먼저 본다.

GC 가 원인이면 튜닝부터 시도한다. GOGC 를 올리면 메모리를 더 쓰는 대신 GC 주기가 줄고, GOMEMLIMIT 로 메모리 상한을 함께 지정할 수 있다. 데이터를 포인터 없는 형태로 바꾸거나, mmap 으로 Go 힙 밖에 두는 방법도 있다. 다만 직렬화 비용이 들고 포인터 구조를 그대로 쓸 수 없다. 데이터가 작으면 여기서 끝난다. 튜닝으로 줄일 수 없는 것은 포인터가 많은 장수명 데이터가 힙에 있는 한 GC 주기마다 반복되는 순회 비용이다. 이 비용을 없애려면 데이터를 다른 힙으로 옮겨야 한다.

구성 선택지#

구성얻는 것대가
전부 Go배포·디버깅·채용이 단순하다장수명 데이터가 Go 힙에 남아 GC 비용을 부담한다
전부 RustGC 가 없다I/O·오케스트레이션 코드까지 Rust 로 작성해야 해서 개발 속도가 느려진다
cgo 로 Rust·C++ 라이브러리 연결데이터가 C 힙에 있어 Go GC 가 보지 않는다호출마다 cgo 비용이 붙고, 라이브러리 장애가 Go 프로세스를 함께 종료시킨다
연산을 별도 서비스로힙 분리, 독립 스케일요청마다 네트워크 왕복이 추가된다
연산을 같은 Pod 의 별도 프로세스로힙 분리, 네트워크 없음, 프로세스 단위 장애 격리프로세스 간 통신 비용과 배포 복잡도

cgo 연결은 GC 문제를 해결하지만 장애 격리를 잃는다. 추론 엔진의 메모리 오류 하나가 요청을 처리하는 프로세스 전체를 종료시킨다.

별도 서비스는 데이터를 자기 프로세스에 들고 있으므로 데이터를 옮기지 않는다. 대신 요청마다 네트워크 왕복이 생겨 GC 꼬리 대신 네트워크 꼬리가 생긴다. 원격 캐시는 사정이 더 나쁘다. 데이터 자체를 네트워크로 가져와야 하고, 캐시를 최신 상태로 유지하는 일도 생긴다. 데이터가 수백 MB 단위면 요청마다 가져올 수도 없다.

같은 Pod 의 별도 프로세스는 힙을 나누고 네트워크를 거치지 않는다.

Pod 안의 컨테이너는 네트워크 네임스페이스와 볼륨을 공유한다. 두 프로세스는 localhost TCP 로도 통신할 수 있지만, 공유 볼륨의 Unix Domain Socket(UDS)을 쓰면 TCP/IP 스택도 거치지 않고 같은 커널 안에서 통신이 끝난다. ms 단위 네트워크 왕복을 피하고 그보다 작은 프로세스 간 통신 비용만 낸다.

Rust 프로세스에는 GC 가 없다. 해제 시점이 소유권 규칙에 따라 대부분 컴파일 시점에 정해지고, Arc 같은 참조 카운팅도 해당 객체만 관리한다. 런타임에 힙 전체를 순회하는 단계가 없다. 사이드카로 얻는 것은 처리 속도보다 지연의 예측 가능성이다.

연산형 사이드카#

사이드카라는 말을 들으면 Envoy 같은 프록시가 먼저 떠오른다. 서비스 메시의 사이드카는 애플리케이션 트래픽을 가로채 mTLS, retry, 라우팅을 대신 처리한다. 애플리케이션은 사이드카의 존재를 몰라도 된다.

연산형 사이드카는 애플리케이션이 명시적으로 호출하고, 도메인 로직의 일부를 수행한다. 사이드카가 없으면 요청을 처리할 수 없다.

항목프록시형 사이드카연산형 사이드카
호출 방식트래픽을 투명하게 가로챈다애플리케이션이 직접 호출한다
담당네트워크 정책 (mTLS, retry, 관측)도메인 연산 (추론, 조회, 집계)
애플리케이션 의존없다요청 처리에 필수다

마이크로서비스는 도메인과 팀을 기준으로 서비스를 나눈다. 연산형 사이드카는 도메인이 하나인 서비스 안에서 런타임 특성을 기준으로 프로세스를 나눈다. I/O 와 오케스트레이션은 Go 가, 큰 상태와 수치 연산은 Rust 가 맡는다. 서비스는 하나이고 프로세스만 둘 이상이다.

Kubernetes 1.29 에서 Beta 로 기본 활성화된 native sidecar 를 쓰면 이 관계를 Pod 명세로 표현할 수 있다. 공식 문서에 따르면 initContainers 에 restartPolicy: Always 를 지정한 컨테이너가 사이드카가 되고, Pod 의 수명 동안 계속 실행된다. init container 로 선언되므로 메인 컨테이너보다 먼저 시작되고, Pod 가 종료될 때 kubelet 은 메인 컨테이너가 완전히 멈춘 뒤 사이드카를 종료한다. 일반 컨테이너로 나란히 선언하면 이런 순서가 보장되지 않는다. 이 기능은 1.33 에서 Stable 이 됐다.

사이드카 구성의 비용#

이 구조는 마이크로서비스의 독립 배포와 독립 스케일을 포기하고 지연을 얻는다. 포기한 것은 다음 비용으로 나타난다.

  • 독립 스케일 불가: 사이드카만 바빠도 Pod 전체를 늘려야 한다. Go 쪽 자원이 남아도 함께 늘어난다
  • 상태 중복: 사이드카의 데이터가 복제본마다 따로 적재된다. 복제본을 늘리면 같은 데이터가 그만큼 메모리를 더 쓴다
  • 기동과 수명의 결합: 사이드카가 기동에 실패하면 메인 컨테이너도 시작되지 않는다
  • 추적 어려움: 프로세스 사이 통신이 네트워크를 거치지 않아 네트워크 트레이스가 남지 않는다. 메시지마다 요청 ID 를 넣어야 어느 요청이 어디서 느려졌는지 추적할 수 있다
  • 두 언어의 운영 부담: 장애가 났을 때 Rust 코드를 읽을 사람이 팀에 있어야 한다

기동 순서와 트래픽 수신은 별개다. native sidecar 는 메인 컨테이너의 시작 시점을 사이드카 기동 뒤로 미룰 뿐이고, Pod 가 트래픽을 받는 시점은 readiness 가 정한다. 사이드카가 데이터를 처음 적재하기 전에 readiness 가 통과하면, Pod 가 트래픽을 받는데 사이드카 호출은 실패하는 구간이 생긴다. readiness 판정에 첫 적재 완료를 포함해야 한다.

사이드카 분리 기준#

연산이 하나 더 필요해지면 기존 사이드카에 추가하거나 새 사이드카를 만든다. 기존 사이드카에 추가하면 통신 경로와 배포 설정을 그대로 쓰므로 변경이 작다. 새 사이드카는 컨테이너 정의, 배포 설정, 호출 경로, 모니터링을 새로 갖춰야 한다.

새 사이드카로 얻는 주된 이점은 장애 격리다. 한 연산이 죽거나 느려져도 다른 연산은 영향을 받지 않고, 재시작과 자원 상한도 따로 지정할 수 있다. 그래서 분리 여부는 두 연산이 함께 실패해도 되는지로 판단한다. 연산별 호출 실패율과 지연을 나눠 수집해 두면 이 판단을 지표로 할 수 있다.

채택 기준#

사이드카가 맞는 경우:

  • GC 진단으로 원인을 확인했고 튜닝으로는 지연 예산을 맞추지 못한다
  • 요청당 여러 번 호출하고 지연 예산이 ms 단위다
  • 메인 서비스와 스케일 특성이 같다

별도 서비스가 맞는 경우:

  • 연산 쪽만 독립적으로 스케일해야 한다
  • 큰 상태를 여러 소비자가 함께 쓴다
  • 호출이 드물거나 비동기로 처리해도 된다

지연 예산이 넉넉하거나 데이터가 작으면 둘 다 필요 없다. 한 언어, 한 프로세스로 두고 튜닝하는 편이 운영 비용이 낮다.

마무리#

Go 서비스에 Rust 사이드카를 붙이는 결정은 응답 상한이 꼬리 지연을 문제로 만들고, 진단이 그 원인을 Go 힙의 장수명 데이터로 지목한 뒤에 성립한다. 같은 Pod 의 프로세스로 옮기면 데이터는 다른 힙에 있고 통신은 네트워크를 거치지 않는다. 대신 독립 스케일과 수명의 분리를 포기한다. 이 교환이 지연 예산 안에서 이득일 때만 사이드카를 쓴다.
