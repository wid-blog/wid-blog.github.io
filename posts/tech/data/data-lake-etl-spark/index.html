백엔드 엔지니어가 본 데이터레이크와 ETL

서비스 DB 를 주로 다루다 데이터 파이프라인 옆에서 일하게 되면 데이터레이크, ETL, Spark 같은 말이 동시에 들어온다. 처음에는 같은 데이터를 왜 여러 번 복사하는지, 서비스 DB 의 복제본으로는 왜 부족한지가 궁금했다. 백엔드에서 알던 개념과 이어 붙여 보니 용어가 정리됐다.

저장과 변환을 나눠서 보면 된다. 데이터레이크는 원본을 지우지 않고 저렴하게 보존하는 저장소다. 그 안에 정제 정도가 다른 raw·staging·mart 계층이 놓이고, 한 계층에서 다음 계층으로 데이터를 넘기는 일이 변환(ETL/ELT)이다. Spark 는 그 변환을 여러 머신에 나눠 실행하는 엔진이다.

OLTP 와 OLAP#

서비스 DB 는 OLTP(Online Transaction Processing)용으로 설계된다. 주문 한 건을 넣고, 회원 한 명을 조회하고, 재고 하나를 줄인다. 질의 하나가 적은 행을 건드리고, 인덱스와 트랜잭션이 그 행을 빠르고 정확하게 찾아 준다.

분석 질의는 반대다. “지난달 도시별 매출"은 주문 테이블 전체를 훑고 금액 컬럼 하나만 더한다. 이런 질의를 OLAP(Online Analytical Processing)라고 부른다. 서비스 DB 에서 OLAP 질의를 실행하면 긴 스캔이 디스크와 버퍼 캐시를 차지해서 서비스 요청이 느려진다. 복제본에서 실행하면 서비스는 지킬 수 있지만, 행 단위로 저장된 데이터를 전부 읽는 비용은 그대로다.

차이는 디스크에 놓이는 순서에서 생긴다. 행 저장은 한 행의 컬럼들이 붙어 있어서 한 건을 통째로 읽고 쓰기 좋다. 열 저장은 같은 컬럼의 값이 붙어 있어서 필요한 컬럼만 읽는다. 같은 타입의 값이 모여 있으니 압축도 잘 된다.

분석용 저장소와 파일 포맷이 열 저장을 쓰는 이유가 여기 있다. 데이터레이크에서 주로 쓰는 Apache Parquet 이 대표적인 열 저장 파일 포맷이다. Parquet 은 컬럼마다 최솟값·최댓값 같은 통계를 함께 기록한다. 그래서 조건에 맞지 않는 구간은 읽지 않고 건너뛴다.

데이터 웨어하우스와 데이터레이크#

분석용 저장소의 출발은 데이터 웨어하우스(Data Warehouse)다. 여러 서비스 DB 의 데이터를 정해진 스키마의 테이블로 옮겨 놓고 SQL 로 분석한다. 스키마를 먼저 정하고, 맞지 않는 데이터는 들어오기 전에 걸러진다. 이것을 쓰기 시점 스키마(Schema-on-write)라고 한다. 백엔드의 RDB 와 감각이 같다. 웨어하우스는 저장과 연산이 한 시스템에 있어서, 데이터를 넣은 곳에서 바로 SQL 을 실행한다.

웨어하우스는 정돈된 대신 들어오는 데이터에 제약이 많다. 클릭 로그처럼 형식이 자주 바뀌는 이벤트, 외부에서 받은 파일, 아직 쓸모가 정해지지 않은 데이터는 스키마를 먼저 정하기 어렵다. 저장 비용도 비쌌다.

데이터레이크(Data Lake)는 이 순서를 바꾼다. S3, GCS 같은 오브젝트 스토리지에 원본 파일을 받은 그대로 보존하고, 구조는 읽는 쪽이 정한다. 이것이 읽기 시점 스키마(Schema-on-read)다. 저장 비용이 낮고 형식 제약이 없어서 일단 다 남길 수 있다. 대신 레이크는 파일 저장소일 뿐이라 연산 기능이 없다. 파일을 읽어 계산하는 일은 별도 엔진이 맡는다.

대가도 분명하다. 누가 어떤 형식으로 무엇을 넣었는지 기록하지 않으면 레이크는 금방 아무도 믿지 못하는 파일 더미가 된다. 이런 상태를 데이터 늪(Data Swamp)이라고 부른다. 파일 묶음은 DB 의 테이블이 아니어서 트랜잭션도, 스키마 강제도, 동시 쓰기 제어도 없다. 쓰기 도중 실패하면 반쯤 쓴 파일이 그대로 남는다.

레이크하우스(Lakehouse)는 레이크의 저렴한 저장과 열린 파일 포맷을 유지하면서 웨어하우스가 주던 성질을 되돌리려는 구성이다. 파일 묶음에 테이블 포맷(Table Format)을 적용한다. Apache Iceberg, Delta Lake, Apache Hudi 같은 테이블 포맷은 “지금 이 테이블을 이루는 파일이 무엇인가"를 따로 기록하고, 그 기록으로 원자적 커밋과 스키마 관리를 제공한다.

ETL 과 ELT#

여기까지가 저장이고, 다음은 변환이다. 원천에서 꺼내고(Extract), 모양을 바꾸고(Transform), 목적지에 넣는다(Load). 순서에 따라 이름이 갈린다.

  • ETL: 변환한 뒤에 적재한다. 웨어하우스에는 정제된 테이블만 들어가고, 원본은 파이프라인을 거치며 버려진다
  • ELT: 원본을 먼저 적재하고, 변환은 적재한 뒤에 한다. 원본이 남아 있어서 변환 규칙이 바뀌면 다시 실행할 수 있다

저장 비용이 낮아지고 연산 엔진이 강해지면서 ELT 가 일반적인 선택이 됐다. 웨어하우스에서는 변환도 웨어하우스 안의 SQL 로 실행한다. 레이크에서는 Spark 같은 엔진이 레이크의 파일을 읽어 변환하고 결과를 다시 레이크에 쓴다. 저장소와 연산 엔진이 분리된 구성이다.

백엔드의 이벤트 로그와 읽기 모델(CQRS)과 닮은 점이 있다. 일어난 일을 그대로 쌓아 두면, 그것을 읽기 좋게 만든 결과물은 언제든 다시 만들 수 있다.

raw, staging, mart 계층#

ELT 를 하면 같은 데이터가 정제 정도에 따라 여러 계층(Layer)에 놓인다. 계층의 이름은 팀마다 다르다. raw·staging·mart 도 쓰고, bronze·silver·gold(메달리온 아키텍처)라고도 부른다. 역할은 대체로 비슷하다.

  • raw: 원천에서 받은 그대로 둔다. 고치지 않고 추가만 한다. 주로 파이프라인 자신이 읽고, 변환에 버그가 있었거나 규칙이 바뀌면 여기서 다시 시작한다
  • staging: 원천 하나를 정리한다. 타입을 맞추고, 이름을 통일하고, 중복과 깨진 행을 걸러 낸다. 아직 원천의 모양을 크게 벗어나지 않고, 주로 데이터 엔지니어가 다음 변환의 입력으로 쓴다
  • mart: 질문 단위로 만든다. 여러 원천을 조인하고 집계해서 “일별 상품 매출”, “시간별 가입자 수” 같은 테이블을 둔다. 대시보드와 분석, 모델 학습은 주로 이 계층을 읽는다

앞 계층이 남아 있으면 뒤 계층은 언제든 다시 만들 수 있다. 버그를 고친 뒤 지난 기간을 다시 계산하는 재처리가 이 성질에 기댄다. mart 를 읽는 사람은 원천의 지저분함을 몰라도 되고, 지표 정의는 mart 한 곳에서 관리한다. 계층마다 책임이 나뉜다.

재처리를 하려면 변환 잡이 같은 입력에는 같은 결과를 내야 한다. 같은 날짜를 두 번 실행했다고 행이 두 배가 되면 재처리를 할 수 없다. 그래서 변환은 대개 날짜별 디렉토리(dt=2026-11-01 같은)를 통째로 다시 쓰는 방식으로 짠다. 백엔드의 멱등 API 와 같은 요구다. 다만 파일을 통째로 덮어쓰는 방식은 멱등이어도 원자적이지 않다. 덮어쓰는 도중 실패하면 반쯤 바뀐 디렉토리가 남는다. 테이블 포맷이 메우는 것이 이 간극이다.

분산 처리 엔진 Spark#

변환을 한 머신에서 실행하면 금방 한계에 도달한다. 하루치 이벤트를 읽는 데만 몇 시간이 걸리고, 재처리할 기간이 길어지면 처리 시간이 하루를 넘는다. Apache Spark 는 이 변환을 여러 머신에 나눠 실행하는 분산 처리 엔진이다. 백엔드 엔지니어에게는 SQL 이나 DataFrame API 로 짠 배치 잡을 클러스터에서 나눠 실행해 주는 도구에 가깝다.

Spark 의 실행 구조는 driver 하나와 여러 executor 로 이뤄진다. driver 는 사용자 코드를 실행하면서 실행 계획을 세우고 일을 나눠 준다. executor 는 실제 데이터를 읽고 계산한다. 데이터는 partition 단위로 쪼개지고, partition 하나를 처리하는 일이 task 하나가 된다. partition 이 많으면 여러 executor 가 동시에 처리한다. 이 partition 은 메모리에서 처리를 나누는 단위라서, 앞에서 본 날짜별 디렉토리와는 다른 개념이다.

events = spark.read.parquet("s3://lake/raw/events/dt=2026-11-01/")
clicks = events.filter(events["type"] == "click")         # 아직 실행하지 않는다
by_user = clicks.groupBy("user_id").count()               # 아직 실행하지 않는다
by_user.write.mode("overwrite").parquet(
    "s3://lake/mart/clicks_by_user/dt=2026-11-01/"         # 여기서 실행된다
)

filter 와 groupBy 는 transformation 이라서 호출해도 바로 실행되지 않는다. Spark 는 계획만 쌓아 두다가 결과가 필요한 action(여기서는 write)을 만나면 전체 계획을 최적화해서 실행한다. 이것을 지연 평가(Lazy Evaluation)라고 한다. 계획 전체를 본 뒤에 실행하므로, 필요한 컬럼만 읽고 조건을 파일 읽기 단계에서 미리 거르는 최적화를 함께 적용할 수 있다.

비용은 transformation 의 종류에 따라 크게 갈린다. filter 처럼 각 partition 을 다른 partition 과 상관없이 처리하는 것을 narrow 라고 한다. groupBy 처럼 같은 키를 가진 행이 한 곳에 모여야 하는 것은 wide 라고 하고, join 도 대개 wide 다. wide transformation 은 executor 사이에서 데이터를 다시 나눠 보내는 shuffle 을 일으킨다. 실행 계획은 shuffle 을 경계로 stage 로 나뉜다. 그림은 이 흐름을 단순화한 것이다.

Spark 문서는 shuffle 을 비싼 연산으로 설명한다. 디스크 I/O, 직렬화, 네트워크 I/O 를 함께 일으키기 때문이다. Spark 잡이 느릴 때 가장 먼저 살피는 곳이 shuffle 이다. 한 키에 행이 몰리면 그 키를 맡은 task 하나만 오래 걸리는데, 이것을 skew 라고 한다. 잡을 짤 때는 shuffle 앞에서 행과 컬럼을 최대한 줄이는 것이 기본이다.

채택 기준#

레이크와 Spark 는 데이터가 커지면 자연스럽게 따라오는 도구지만, 처음부터 필요한 것은 아니다.

레이크와 분산 처리가 맞는 경우:

  • 원본을 오래 보존하고 규칙이 바뀔 때마다 다시 계산해야 한다
  • 하루치 데이터의 처리 시간이 한 머신으로는 정해진 시간 안에 끝나지 않는다
  • 형식이 다른 원천 여러 개를 한 곳에서 조인한다

서비스 DB 복제본이나 단일 노드 도구로 충분한 경우:

  • 분석 대상이 서비스 DB 테이블 몇 개이고 크기가 작다
  • 질문이 정해져 있어서 원본을 다시 읽을 일이 드물다
  • 파이프라인을 운영할 사람이 따로 없다

작게 시작할 때는 서비스 DB 복제본이나 관리형 웨어하우스에 ELT 로 넣고, 원본 보존과 재처리가 부담이 될 때 레이크와 Spark 로 옮기는 순서를 주로 밟는다. 스트리밍 처리와 잡 스케줄링(Airflow 같은 오케스트레이터)은 이 구성 위에 더해지는 별도 주제다.

마무리#

원본이 남아 있고 변환이 멱등이면 뒤 계층은 언제든 다시 만들 수 있다. 데이터레이크는 그 원본을 보존하고, 계층은 정제 단계를 나누며, Spark 는 계층 사이의 변환을 여러 머신에서 실행한다. 저장과 변환을 나눠 보면 각 도구가 어느 쪽 문제를 푸는지 보인다.
