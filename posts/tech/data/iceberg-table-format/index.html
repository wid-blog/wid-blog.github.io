파일 묶음을 테이블로 만드는 Iceberg

RDB 에서는 커밋하면 변경이 다 보이거나 하나도 안 보인다. 컬럼을 추가해도 테이블은 그대로 테이블이고, 다른 트랜잭션이 쓰는 중에도 읽기는 일관된 상태를 본다. 오브젝트 스토리지에 Parquet 파일을 디렉토리별로 쌓아 두면 SQL 로 조회는 되지만 이 성질들이 사라진다. 백엔드에서 당연하게 기대하던 것들이 파일 묶음에서 어떻게 다시 만들어지는지가 궁금했다.

Apache Iceberg 는 “지금 이 테이블을 이루는 파일이 무엇인가"를 metadata 파일로 기록하고, 최신 metadata 파일을 가리키는 포인터 하나를 원자적으로 바꾸는 것을 커밋으로 삼는다. 커밋이 원자적이 되고, 이전 상태가 snapshot 으로 남는다. 여기에 컬럼 ID 와 파티션 변환 같은 metadata 설계가 더해져 스키마와 파티션 방식도 파일을 다시 쓰지 않고 바꿀 수 있다. 대신 쓸 때마다 옛 파일과 snapshot 이 남아서, 그것을 주기적으로 정리하는 운영 작업이 따라온다.

Hive 식 디렉토리 테이블#

Iceberg 이전에 흔히 쓰던 방식은 Hive 식 디렉토리 테이블이다. 테이블은 디렉토리 하나이고, 그 아래 파일 전부가 테이블의 데이터다. 파티션은 하위 디렉토리 이름으로 나눈다.

s3://lake/events/dt=2026-11-01/part-0001.parquet
s3://lake/events/dt=2026-11-01/part-0002.parquet
s3://lake/events/dt=2026-11-02/part-0001.parquet

“테이블 = 이 디렉토리 아래 파일 전부"라는 정의가 간단한 대신 대가가 있다.

  • 목록 조회 비용: 쿼리를 계획하려면 디렉토리를 나열해서 파일을 찾아야 한다. 오브젝트 스토리지의 목록 조회는 느리고, 파티션이 늘어날수록 호출도 늘어난다
  • 부분 쓰기 노출: 잡이 파일 열 개 중 다섯 개를 쓴 시점에 누가 읽으면 다섯 개만 보인다. 잡이 실패하면 반쯤 쓴 파일이 그대로 남는다. 두 잡이 같은 파티션을 동시에 덮어쓰면 결과를 보장할 수 없다
  • 사용자가 알아야 하는 파티션 컬럼: dt 로 나눈 테이블을 event_time 조건으로만 거르면 파티션을 건너뛰지 못하고 전부 읽는다. Hive 는 파티션 값을 검증하지도 못한다. Iceberg 문서는 20181201 대신 2018-12-01 처럼 형식을 틀리게 쓰면 쿼리가 실패하지 않고 조용히 틀린 결과를 낸다고 설명한다
  • 스키마 변경: 파일마다 스키마가 다를 수 있다. 컬럼을 이름으로 맞추면 지운 컬럼의 이름을 다시 쓸 때 옛 값이 되살아날 수 있고, 위치로 맞추면 중간 컬럼을 지울 수 없다

백엔드 감각으로 옮기면 트랜잭션 없이 여러 행을 하나씩 쓰는 것과 비슷하다. 중간 상태가 보이고, 실패하면 일부만 남는다.

Iceberg 의 metadata 트리#

테이블 포맷(Table Format)인 Iceberg 는 디렉토리 대신 파일 목록을 테이블의 기준으로 삼는다. Iceberg spec이 정의하는 구조는 다섯 단계다.

  • catalog: 테이블 이름을 현재 metadata 파일의 위치에 연결한다. 테이블마다 포인터 하나를 기록한다
  • metadata 파일: 테이블의 스키마, 파티션 방식(partition spec), snapshot 목록, 그중 현재 snapshot 을 기록한다. 테이블 상태가 바뀔 때마다 새 metadata 파일이 생긴다
  • manifest list: snapshot 마다 하나씩 있다. 그 snapshot 을 이루는 manifest 파일들을 나열한다
  • manifest: data file 목록이다. 파일마다 파티션 값과 컬럼별 최솟값·최댓값 같은 통계를 함께 적는다
  • data file: 실제 데이터가 든 Parquet 같은 파일이다

읽기는 catalog 에서 data file 쪽으로 진행한다. catalog 에서 현재 metadata 파일을 찾고, 현재 snapshot 의 manifest list 를 읽고, manifest 의 파티션 값과 통계로 조건에 맞지 않는 파일을 걸러 낸 뒤 남은 data file 만 연다. 디렉토리를 나열하지 않는다. spec 은 목표 중 하나로 스캔할 파일을 계획하는 데 원격 호출이 O(1) 번만 들게 하는 것을 꼽는다.

포인터 교체로 하는 커밋#

쓰기도 같은 구조를 따른다. 새 data file 을 먼저 쓰고, 그 파일들을 담은 manifest, 새 snapshot 의 manifest list, 새 metadata 파일을 차례로 쓴다. 여기까지는 아무도 새 파일을 모른다. 마지막으로 catalog 의 포인터를 새 metadata 파일로 바꾸는 순간 커밋이 일어난다.

포인터 교체는 원자적이다. spec 은 모든 테이블 변경이 새 metadata 파일을 만들고, 원자적 교체로 옛 metadata 를 대신한다고 정의한다. 읽는 쪽은 교체 전의 테이블 아니면 교체 후의 테이블만 본다. 커밋 전에 잡이 실패하면 새로 쓴 파일은 어느 metadata 에도 들어가지 않으므로 읽는 쪽에게 보이지 않는다.

여러 잡이 동시에 쓰면 낙관적 동시성(Optimistic Concurrency)으로 처리한다. 각 잡은 자기가 읽은 metadata 를 기준으로 새 metadata 를 만들고, catalog 에는 “현재 포인터가 내가 읽은 그 파일일 때만 바꿔 달라"고 요청한다. 그사이 다른 잡이 먼저 커밋했다면 교체가 거부된다. 거부된 쪽은 새 상태를 기준으로 다시 시도하고, 같은 파일을 바꾸는 변경끼리 겹쳤다면 커밋이 실패할 수 있다. 백엔드의 UPDATE ... WHERE version = ? 낙관적 락과 같은 방식으로 동작한다. 같은 테이블에 동시에 쓰는 잡이 많을수록 재시도가 늘어난다.

읽기는 시작할 때 고른 snapshot 을 끝까지 쓴다. spec 은 읽기가 동시 쓰기와 격리되고 항상 커밋된 snapshot 을 본다고 명시한다. 읽는 도중 새 커밋이 들어와도 그 쿼리는 처음 본 파일 목록으로 계속 읽는다. RDB 의 MVCC(다중 버전 동시성 제어)가 주는 snapshot 읽기와 감각이 같다.

snapshot, 스키마, 파티션#

snapshot 과 과거 시점 조회#

커밋마다 새 snapshot 이 생기고, 이전 snapshot 은 metadata 에 남는다. 이전 snapshot 이 가리키는 파일도 지우지 않으므로 과거 시점의 테이블을 그대로 조회할 수 있다. 이것을 과거 시점 조회(Time Travel)라고 한다. Spark SQL 에서는 시각이나 snapshot ID 로 지정한다.

SELECT * FROM db.events TIMESTAMP AS OF '2026-11-01 00:00:00';
SELECT * FROM db.events VERSION AS OF 10963874102873;

잘못된 적재가 들어간 뒤 직전 상태와 비교하거나, 특정 시점의 결과를 재현할 때 쓴다. 테이블을 이전 snapshot 으로 되돌리는 프로시저도 있다.

스키마 변경#

Iceberg 는 컬럼마다 고유 ID 를 붙여서 추적한다. data file 에서 컬럼을 찾을 때도 이름이 아니라 ID 를 쓴다. 그래서 컬럼 추가·삭제·이름 변경·순서 변경, 그리고 int 를 long 으로 넓히는 식의 타입 확장이 metadata 변경만으로 끝난다. data file 을 다시 쓰지 않는다. 이름을 바꿔도 ID 는 그대로라 옛 파일의 값을 계속 읽고, 지운 컬럼과 같은 이름으로 새 컬럼을 만들어도 ID 가 달라서 옛 값이 되살아나지 않는다.

큰 테이블에 ALTER TABLE ... ADD COLUMN 을 실행할 때 걱정하던 테이블 복사나 잠금이 여기서는 생기지 않는다.

숨은 파티셔닝#

Iceberg 에서는 파티션 값을 컬럼에서 변환(Transform)으로 도출한다. 테이블을 만들 때 “event_time 의 날짜로 나눈다"고 선언하면, 쓰는 쪽은 별도 dt 컬럼을 채우지 않고 읽는 쪽도 event_time 조건만 건다. Iceberg 가 조건에서 해당 날짜 파티션을 찾아 나머지를 건너뛴다. 이것을 숨은 파티셔닝(Hidden Partitioning)이라고 부른다.

CREATE TABLE db.events (
    event_id   STRING,
    user_id    STRING,
    event_time TIMESTAMP
) USING iceberg
PARTITIONED BY (days(event_time));

시간 단위(연·월·일·시) 외에 해시로 나누는 bucket, 문자열·숫자를 자르는 truncate 같은 변환도 있다. 파티션 컬럼이 쿼리에 드러나지 않으니 사용자가 형식을 틀릴 일이 없다.

파티션 방식을 바꾸는 것도 metadata 변경이다. 하루 단위로 나누다가 데이터가 늘어 시간 단위로 바꾸면, 이미 쓴 파일은 옛 방식 그대로 두고 새 파일만 새 방식으로 쓴다. 쿼리는 파티션 방식별로 따로 계획해서 합친다. 문서는 이것을 split planning 이라고 부른다. Hive 식 테이블이라면 테이블 전체를 다시 써야 하는 변경이다.

쓰기 방식#

Spark 에서 Iceberg 테이블에 쓰는 방식은 append, overwrite, MERGE INTO 가 대표적이다.

  • append: 새 data file 을 추가한다. 기존 파일은 건드리지 않는다. 이벤트 로그 적재에 주로 쓰인다
  • overwrite: INSERT OVERWRITE 로 파티션을 통째로 바꾼다. Iceberg 문서는 dynamic overwrite 모드를 권장하는데, 이 모드에서는 SELECT 결과에 행이 있는 파티션만 교체된다
  • MERGE INTO: 키를 기준으로 행 단위 갱신·삭제·삽입을 한다. 문서는 영향받는 data file 만 바꿀 수 있다는 이유로 INSERT OVERWRITE 대신 MERGE INTO 를 권한다

행 단위 변경은 두 가지 방식으로 처리된다. write.delete.mode·write.update.mode·write.merge.mode 테이블 속성으로 고르며, 기본값은 copy-on-write 다.

  • copy-on-write: 바뀐 행이 든 data file 을 통째로 다시 쓴다. 쓰기는 비싸지만 읽을 때 추가 작업이 없다
  • merge-on-read: 원래 파일을 두고 “이 파일의 몇 번째 행이 지워졌다"는 삭제 정보를 따로 쓴 뒤 읽을 때 합친다. 쓰기는 가볍지만 삭제 정보가 쌓이면 읽기가 느려진다

삭제 정보는 format v2 의 delete file 로 시작했고, format v3 에서는 파일별 비트맵인 deletion vector 로 바뀌었다. 어느 format 을 쓸 수 있는지는 엔진과 버전에 따라 다르다.

늦게 도착한 데이터와 멱등 재작성#

이벤트는 항상 제때 오지 않는다. 앱이 오프라인이었다가 나중에 보내거나, 외부 원천이 하루 늦게 파일을 넘기기도 한다. 이미 처리한 날짜에 행이 더 들어와야 하는 상황이다.

늦은 행만 골라 append 하면 간단해 보이지만, 잡을 다시 실행할 때 같은 행이 또 붙는다. 데이터 파이프라인에서 흔히 쓰는 해법은 매번 최근 며칠 창을 원천 데이터에서 통째로 다시 계산해서 dynamic overwrite 로 덮어쓰는 것이다. 같은 입력이면 같은 결과가 나오고, 몇 번을 실행해도 행이 늘지 않는다. 이런 성질을 멱등(Idempotent)이라고 한다. Iceberg 에서는 덮어쓰기가 커밋 한 번으로 일어나므로 읽는 쪽은 옛 파티션 아니면 새 파티션만 본다. 창이 커서 다시 계산하는 비용이 부담되면 키 기준 MERGE INTO 로 바꾸는 선택지도 있다.

운영 과제#

Iceberg 의 커밋은 파일을 고치지 않고 새로 쓴 뒤 포인터만 바꾼다. 옛 파일은 이전 snapshot 이 가리키고 있어서 바로 지우지 못한다. 그래서 시간이 지나면 작은 파일, 오래된 snapshot, 아무도 가리키지 않는 파일이 쌓인다. Iceberg 문서는 이 정리를 별도 유지보수 작업으로 안내한다.

작은 파일 합치기#

자주 적재할수록 커밋마다 작은 파일이 생긴다. 문서는 작은 data file 이 많으면 metadata 가 불필요하게 커지고 파일을 여는 비용 때문에 쿼리가 느려진다고 설명한다. rewrite_data_files 프로시저가 작은 파일을 묶어 큰 파일로 다시 쓴다. merge-on-read 를 쓰는 테이블이라면 쌓인 삭제 정보를 정리하는 일도 여기에 더해진다.

CALL catalog.system.rewrite_data_files(
    table => 'db.events',
    where => 'event_time < TIMESTAMP "2026-11-07 00:00:00"'
);

합치기도 커밋이다. 큰 파일을 새로 쓰고 snapshot 을 바꾼다. 옛 작은 파일은 이전 snapshot 이 가리키는 동안 저장소에 남는다.

where 는 합칠 범위를 좁힌다. 늦은 데이터 때문에 최근 며칠을 매번 다시 쓰는 테이블이라면, 그 구간을 합쳐도 곧 덮어써질 파일을 다시 쓰는 셈이다. 같은 파티션에 재작성 커밋과 합치기 커밋이 겹치면 한쪽이 충돌로 실패할 수도 있다. 그래서 합치기는 다시 쓰는 창 밖의 파티션으로 한정한다.

snapshot 만료#

snapshot 이 남아 있는 한 그 snapshot 이 가리키는 파일도 지울 수 없다. expire_snapshots 는 정한 기간보다 오래된 snapshot 을 metadata 에서 지우고, 남은 snapshot 어느 것도 가리키지 않게 된 data file 을 삭제한다. 만료된 시점의 테이블은 더 이상 조회할 수 없다.

보존 기간을 길게 두면 과거 시점으로 돌아갈 여지가 크고, 짧게 두면 옛 파일이 빨리 지워져 저장 비용이 준다. 원천 데이터에서 다시 만들 수 있는 테이블이라면 짧게 두는 편이 부담이 적다고 봤다.

고아 파일 삭제#

고아 파일(Orphan File)은 저장소에는 있지만 어느 metadata 도 가리키지 않는 파일이다. 문서는 태스크나 잡의 실패가 이런 파일을 남길 수 있다고 설명한다. 커밋 직전에 실패한 잡의 data file 이 대표적이다. snapshot 만료는 metadata 에 기록된 파일만 지우므로 이런 파일은 따로 찾아야 한다. remove_orphan_files 는 저장소의 파일과 metadata 를 비교해서 어디에도 없는 파일을 지운다.

지금 실행 중인 쓰기가 막 쓴 파일도 커밋 전이라 metadata 에 없다. 이 시점에 정리 작업을 실행하면 곧 커밋될 파일을 고아로 보고 지운다. 문서는 쓰기가 끝나는 데 걸리는 시간보다 짧은 보존 기간으로 고아 파일을 지우는 것이 위험하다고 경고한다. 그래서 일정 시간보다 오래된 파일만 지우도록 여유 기간을 둔다.

채택 기준#

테이블 포맷은 원자성과 스키마 관리를 주지만, 정리 작업을 운영해야 한다.

테이블 포맷이 맞는 경우:

  • 같은 테이블을 여러 잡이 쓰거나, 쓰는 중에도 읽기가 일어난다
  • 파티션을 덮어쓰거나 행 단위로 고치는 재처리가 잦다
  • 스키마와 파티션 방식이 시간이 지나며 바뀐다

디렉토리 + Parquet 로 충분한 경우:

  • 한 잡만 쓰고, 쓰기가 끝난 뒤에만 읽는다
  • 파일을 추가만 하고 고치지 않는다
  • 파일과 파티션 수가 적어서 목록 조회 비용이 문제가 되지 않는다

Delta Lake 와 Apache Hudi 도 같은 문제를 푸는 테이블 포맷이다. 파일 목록을 기록하는 방식과 강점이 조금씩 다르다.

마무리#

오브젝트 스토리지의 파일 묶음은 그 자체로는 테이블이 아니다. Iceberg 는 테이블을 이루는 파일 목록을 metadata 트리로 기록하고, 포인터 하나의 원자적 교체를 커밋으로 삼는다. 파일을 고치지 않고 새로 쓰는 이 방식 덕분에 커밋이 원자적이고 과거 상태가 남지만, 같은 이유로 작은 파일, 오래된 snapshot, 고아 파일이 쌓인다. DB 가 내부에서 처리하던 일을 테이블 포맷과 유지보수 작업이 나눠 맡는다.
