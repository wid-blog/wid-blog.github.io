eBPF 는 커널 소스를 고치거나 모듈을 로드하지 않고, 커널 안의 이벤트 지점에서 사용자가 작성한 프로그램을 실행하는 방식이다. 커널 안에서 실행되는 코드가 커널을 멈추거나 메모리를 망가뜨리면 안 되므로, 커널은 로드 시점에 프로그램을 검증하고 통과한 것만 실행한다. 검증이 가능하도록 프로그램이 할 수 있는 일도 좁혀 둔다. 커널 함수는 정해진 것만 호출하고, 상태는 map 이라는 커널 저장소에만 남긴다.

k8s 네트워크 플러그인(CNI)인 Cilium 과 여러 관측 도구가 eBPF 로 동작한다는 설명은 자주 만나는데, 커널에 “프로그램을 로드한다"는 것이 실제로 어떤 절차인지가 궁금했다. 로드 흐름을 정리하고, colima VM 에서 bpftrace 로 직접 확인했다.

로드 흐름#

ebpf.io 의 설명을 순서대로 놓았다.

  • 컴파일: 커널은 eBPF 프로그램을 bytecode 로 받는다. C 에 가까운 코드를 clang·LLVM 으로 bytecode 로 컴파일한다
  • 로드: bytecode 를 bpf() syscall 로 커널에 넘긴다
  • 검증: verifier 가 프로그램이 안전한지 검사한다. 통과하지 못하면 로드가 실패한다
  • JIT 컴파일: bytecode 를 CPU 아키텍처의 기계어로 번역한다
  • attach: 프로그램을 hook 에 붙인다. 이후 커널이나 애플리케이션이 그 지점을 지날 때마다 프로그램이 실행된다

프로그램이 모은 결과는 map 에 쌓이고, user space 도구는 다시 bpf() syscall 로 map 을 읽는다. 커널 안 프로그램과 user space 사이의 데이터는 주로 map 을 통해 오간다.

bpftrace 는 이 흐름을 한 줄 명령으로 줄인 도구다. README 는 “bpftrace uses LLVM as a compiler backend, and libbpf for interacting with the Linux BPF subsystem” 이라고 설명한다. 스크립트를 LLVM IR 로 만들고, bytecode 로 컴파일해 로드하고, 끝나면 map 을 읽어 출력한다. BCC 는 커널 쪽 코드를 C 로 쓰고 user space 쪽을 Python 이나 Lua 로 쓴다. 한 줄로 끝나는 관찰은 bpftrace 가 간편하다. 커널 쪽 로직이 길거나 user space 에서 결과를 가공해야 하면 BCC·libbpf 처럼 양쪽 코드를 직접 쓰는 방식이 맞다고 봤다.

verifier#

커널 모듈은 로드된 뒤 무엇을 하는지 커널이 검사하지 않는다. eBPF 는 로드 시점에 프로그램을 검사하고, 안전하다고 증명하지 못하면 로드하지 않는다. 로드 자체에도 권한이 필요하다. ebpf.io 에 따르면 비특권 eBPF 가 켜져 있지 않으면 root 또는 CAP_BPF 가 있어야 한다.

ebpf.io 와 커널 verifier 문서 가 설명하는 검사 항목은 다음과 같다.

  • 종료: 프로그램은 끝까지 실행되어야 한다. 루프는 종료 조건이 반드시 참이 된다고 verifier 가 확인할 수 있을 때만 허용된다 (bounded loop)
  • 미초기화 읽기: 한 번도 쓰지 않은 register 는 읽을 수 없고, stack 도 먼저 쓴 영역만 읽을 수 있다
  • 범위 밖 접근: 메모리 접근은 범위와 정렬을 검사한다
  • NULL 검사: map 조회 결과는 PTR_TO_MAP_VALUE_OR_NULL 타입이고, NULL 이 아님을 확인한 뒤에야 값에 접근할 수 있다
  • 복잡도: 모든 실행 경로를 정해진 상한 안에서 분석할 수 있어야 한다

verifier 는 첫 명령부터 가능한 경로를 모두 따라가며 register 와 stack 의 상태를 추적한다. 경로 수는 분기마다 늘어나므로, 이미 검사한 상태에 현재 상태가 포함되면 그 경로는 더 따라가지 않는다. 커널 문서는 이를 state pruning 이라고 부른다. 종료 검사도 이 경로 추적으로 이뤄진다. 루프의 끝까지 따라갈 수 있어야 종료가 증명되고, 분석이 상한을 넘으면 verifier 는 프로그램을 거부한다.

map#

eBPF 프로그램은 hook 이 실행될 때마다 처음부터 다시 시작한다. 호출 사이에 값을 남기거나 user space 로 결과를 보내려면 map 에 쓴다. 커널 문서 에 따르면 user space 는 bpf() syscall 로 map 을 만들고, 원소를 조회·갱신·삭제한다. map 을 만들면 file descriptor 가 돌아오고, 이후 명령은 이 fd 로 map 을 가리킨다. 커널 안 프로그램은 helper 로 같은 map 에 접근한다.

종류쓰임
HASH · PERCPU_HASH · LRU_HASHkey-value 집계. PERCPU 는 CPU 마다 따로 둔다
ARRAY · PERCPU_ARRAY정수 index 로 접근하는 고정 크기 배열
RINGBUF커널 → user space 이벤트 전달
LPM_TRIE최장 prefix 매칭 (IP 대역 조회)
SOCKMAP · XSKMAP네트워크용. socket 으로 패킷을 넘길 때

RINGBUF 는 CPU 마다 버퍼를 두는 perf buffer 의 대안이다. ringbuf 문서 는 여러 CPU 가 하나의 ring buffer 를 공유하는 MPSC(multi-producer, single-consumer) 구조로 메모리를 더 효율적으로 쓰고 이벤트 순서를 유지한다고 설명한다.

helper 와 kfunc#

eBPF 프로그램은 커널 함수를 직접 호출할 수 없다. 커널이 eBPF 용으로 공개한 helper 와 kfunc 만 호출할 수 있다.

  • helper: bpf_map_lookup_elem, bpf_get_current_comm 처럼 커널이 eBPF 에 제공하는 함수다. ebpf.io 는 helper 를 “a well-known and stable API” 라고 설명한다. 목록은 bpf-helpers(7) 에 있다
  • kfunc: 커널 함수를 eBPF 프로그램이 호출할 수 있게 노출한 것이다. kfunc 문서 는 “Unlike normal BPF helpers, kfuncs do not have a stable interface and can change from one kernel release to another.” 라고 적는다. 제거 예정인 kfunc 에는 KF_DEPRECATED 표시가 붙고, 제거된 뒤에는 그 kfunc 를 호출하는 프로그램을 verifier 가 거부한다

호출도 verifier 가 검사한다. 인자 register 가 helper 의 인자 조건에 맞는지 확인하고, 호출 뒤 R0 를 helper 의 반환 타입으로 설정한다. verifier 가 호출 전후의 상태를 계속 추적할 수 있는 것은 helper·kfunc 의 인자와 반환 타입이 선언되어 있기 때문이고, 임의의 커널 함수 호출을 막는 이유도 여기에 있다고 이해했다.

여러 커널 버전에서 같은 프로그램을 써야 하면 helper 로 해결되는지 먼저 확인하는 쪽이 안전하다고 판단했다. kfunc 는 대상 커널 버전을 정해 두고 쓴다.

hook#

hook 은 프로그램이 실행되는 지점이다. 관측에 자주 쓰는 것은 tracepoint 와 kprobe 이고, 네트워크 경로에는 tc 와 XDP 가 있다.

  • tracepoint: 커널 코드에 미리 정의해 둔 정적 지점이다. syscall 진입·종료, 스케줄러, 블록 I/O 등에 있다. 인자 형식이 정해져 있어 bpftrace -lv 로 필드를 볼 수 있다
  • kprobe · kretprobe: 커널 함수의 진입·반환에 동적으로 붙는다. 커널 kprobes 문서 에 따르면 kprobes 자신을 제외한 커널 대부분에 붙일 수 있다
  • tc: traffic control 계층에서 패킷마다 실행된다
  • XDP: 네트워크 카드(NIC) 드라이버의 수신 경로에서 실행된다

tracepoint 와 kprobe 의 주된 차이는 안정성이다. bpftrace reference guide 는 정적 tracing 을 “Since these are fixed, they may be provided as part of a stable API, and documented.” 로, 동적 tracing 을 “it is not considered a stable API, and the target functions may not be documented outside of their source code.” 로 설명한다. kprobe 가 붙는 커널 함수는 안정 API 가 아니므로 커널 버전이 바뀌면 이름이나 인자가 달라질 수 있다. 인라인된 함수는 kprobe 가 일부 호출을 놓칠 수도 있다. 같은 정보를 tracepoint 로 얻을 수 있으면 tracepoint 를 먼저 쓰는 쪽이 낫다고 판단했다.

실습한 VM 에서 붙일 수 있는 지점의 수다.

$ sudo bpftrace -l 'tracepoint:*' | wc -l
1517
$ sudo bpftrace -l 'tracepoint:syscalls:sys_enter_*' | wc -l
311
$ sudo bpftrace -l 'kprobe:*' | wc -l
61927

bpftrace 실습#

실행 환경은 colima VM (Ubuntu 24.04, kernel 6.8.0, aarch64) 이고, bpftrace v0.20.2 와 bpftool v7.4.0 을 apt 로 설치했다. VM 에는 kubelet·containerd 같은 k8s 구성 요소가 함께 실행 중이다. JIT 는 켜져 있다.

$ cat /proc/sys/net/core/bpf_jit_enable
1

부하는 dd 로 4KB 블록 2만 개를 파일에 쓰고 다시 읽는다. 첫 번째 실습에는 ls·cat 을 200번 반복하는 부하를 더했다.

$ dd if=/dev/zero of=/tmp/ebpf-dd bs=4k count=20000
$ dd if=/tmp/ebpf-dd of=/dev/null bs=4k

지연 히스토그램#

kprobe 로 vfs_read 진입 시각을 thread id(tid) 별로 map 에 적고, kretprobe 에서 반환 시각과의 차이를 hist() 로 모은다. hist() 는 2의 거듭제곱 구간으로 값을 센다.

$ sudo bpftrace -e 'kprobe:vfs_read /comm == "dd"/ { @start[tid] = nsecs; }
    kretprobe:vfs_read /@start[tid]/ { @ns = hist(nsecs - @start[tid]); delete(@start[tid]); }
    interval:s:5 { exit(); }
    END { clear(@start); }'

로드된 프로그램#

bpftrace 가 실행 중일 때 bpftool 로 커널에 로드된 프로그램과 map 을 볼 수 있다. openat 을 프로세스별로 세는 스크립트를 실행해 두고 확인했다.

$ sudo bpftool prog list
...
2796: tracepoint  name tracepoint_syscalls_sys_enter_openat  tag afe1b01453072a6e  gpl
	loaded_at 2026-11-16T20:53:14+0900  uid 0
	xlated 232B  jited 280B  memlock 4096B  map_ids 703
	btf_id 420

xlated 는 bytecode 크기, jited 는 JIT 컴파일로 만든 arm64 기계어 크기다. 목록에는 VM 에이전트가 미리 로드해 둔 lima_ticker 같은 프로그램도 함께 보인다. bytecode 에서 helper 호출과 NULL 검사 분기를 확인할 수 있다.

bpftrace 의 @[comm] = count() 는 PERCPU_HASH map 이 되었다. key 16B 는 comm 의 크기다. 함께 만들어진 ringbuf 는 이름으로 보아 printf 같은 출력을 user space 로 보내는 용도로 보인다.

verifier 거부#

상한이 상수인 루프는 통과한다.

$ sudo bpftrace -e 'BEGIN { $i = 0; while ($i < 10) { $i++; } printf("i=%d\n", $i); exit(); }'
i=10

처음에는 while ($i >= 0) { $i++; } 처럼 끝나지 않는 루프를 시도했는데, 거부되지 않았다. -v 로 verifier 로그를 보니 처리한 명령이 24개뿐이었다. 아무 효과가 없는 루프를 LLVM 이 컴파일 단계에서 없앤 것으로 보인다. 그래서 상한을 실행 시점의 값(nsecs)으로 두고, 루프 안에서 map 을 갱신해 LLVM 이 루프를 없애지 못하게 했다.

$ sudo bpftrace -e 'BEGIN { $i = 0; $n = (int64)nsecs;
    while ($i < $n) { @calls = count(); $i++; } printf("i=%d\n", $i); exit(); }'
Attaching 1 probe...
ERROR: Error loading program: BEGIN (try -v)

-v 로 다시 실행하면 verifier 로그가 출력된다. 로그는 1만 줄이 넘었고, bpftrace 는 로그 버퍼가 부족하다는 에러도 함께 냈다. 끝부분은 다음과 같다.

25: (85) call bpf_map_lookup_elem#1   ; R0_w=map_value_or_null(id=8194,map=AT_calls,ks=4,vs=8)
26: (15) if r0 == 0x0 goto pc-19      ; R0_w=map_value(map=AT_calls,ks=4,vs=8)
27: (79) r1 = *(u64 *)(r0 +0)         ; R0_w=map_value(map=AT_calls,ks=4,vs=8) R1_w=scalar()
28: (07) r1 += 1                      ; R1_w=scalar()
29: (7b) *(u64 *)(r0 +0) = r1         ; R0_w=map_value(map=AT_calls,ks=4,vs=8) R1_w=scalar()
30: (07) r6 += 1                      ; R6_w=8191
31: (6d) if r8 s> r6 goto pc-12
The sequence of 8193 jumps is too complex.
processed 98378 insns (limit 1000000) max_states_per_insn 4 total_states 1237 peak_states 1237 mark_read 3
  • NULL 검사 추적: 25번 조회 직후 R0 는 map_value_or_null 이고, 26번 분기를 지나면 map_value 로 바뀐다. 이 분기 뒤에서만 값을 읽을 수 있다
  • 반복마다 추적: 카운터 $i 가 들어 있는 R6 를 8191 이라는 구체 값으로 추적한다. 상한 $n(R8)을 알 수 없으니 반복마다 새 경로로 보고 계속 따라간 것으로 보인다
  • 복잡도 상한에서 거부: 점프가 8,193번 이어지자 “too complex” 로 거부했다. 명령 처리 상한(1,000,000)에 도달하기 전이다

verifier 는 이 루프가 끝난다는 것을 증명하지 못했다. 반복을 하나씩 따라가다 분석 상한에서 멈췄고, 프로그램은 실행되지 않은 채 거부됐다. 같은 로직을 로드하려면 상한을 상수로 두거나 반복 수를 줄여 verifier 가 분석할 수 있는 형태로 바꿔야 한다.

정리#

eBPF 프로그램은 bytecode 로 커널에 들어가 verifier 를 통과해야 JIT 컴파일을 거쳐 hook 에 붙는다. 안전을 보장하는 것은 verifier 다. helper·kfunc 만 호출하고 상태를 map 에만 남기는 제약은 verifier 가 모든 경로를 추적할 수 있게 하는 조건이다. bpftrace 의 한 줄 명령도 이 흐름을 그대로 따른다. @ 변수는 map 이 되고, 조회 뒤에는 NULL 분기가 들어가며, 끝까지 분석할 수 없는 루프는 로드 단계에서 거부된다.
