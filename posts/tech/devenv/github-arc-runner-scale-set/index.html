GitHub ARC — job 하나가 runner pod 로 실행되고 삭제되기까지

Actions Runner Controller(ARC)는 GitHub Actions 의 self-hosted runner 를 Kubernetes 에서 실행하고 스케일하는 operator 다. 현재 GitHub 이 지원하는 방식은 runner scale set 모드로, job 하나마다 runner pod 하나가 생기고 job 이 끝나면 그 pod 는 삭제된다. VM 에 상주하는 runner 와 달리 job 이 없으면 pod 도 0개까지 줄어든다.

job 하나가 GitHub 의 큐에 들어와 클러스터 안의 pod 로 실행되고 삭제되기까지, 그 사이에서 누가 무엇을 하는지 궁금했다. ARC 저장소의 scale set 모드 문서와 GitHub 공식 문서를 기준으로 확인했고, 작성 시점의 최신 릴리스는 gha-runner-scale-set-0.15.1 이다. 따라가 보면 흐름은 두 연결로 정리된다. listener 는 GitHub 에서 “job 이 들어왔다"는 신호만 받고, job 의 실제 내용은 runner 가 GitHub 에서 직접 받아 온다.

구성 요소#

ARC 는 Helm chart 두 개로 설치한다. gha-runner-scale-set-controller 는 controller manager pod 를 실행하고, gha-runner-scale-set 은 runner 집합 하나를 정의하는 AutoscalingRunnerSet 리소스를 만든다. scale set 을 여러 개 두려면 두 번째 chart 를 여러 번 설치한다.

controller manager 는 리소스 종류별 controller 를 포함하고, 각 controller 는 하위 리소스를 만든다. 모두 actions.github.com/v1alpha1 API 그룹의 custom resource 다.

  • AutoscalingRunnerSet: scale set 하나의 최상위 리소스. GitHub 에 runner scale set 을 등록하고 AutoscalingListener 와 EphemeralRunnerSet 을 만든다
  • AutoscalingListener: listener pod 를 정의한다. listener 는 GitHub 의 Actions Service 와 연결을 유지하며 job 이 들어오기를 기다린다
  • EphemeralRunnerSet: 원하는 runner 수(replicas)를 갖는다. listener 가 이 값을 바꾼다
  • EphemeralRunner: runner 하나. runner pod 하나에 대응한다

job 의 생애주기#

ARC 문서는 흐름을 11단계로 설명한다. 여기서는 준비, 스케일업, 실행, 정리 네 구간으로 묶었다.

준비#

AutoscalingRunnerSet 이 만들어지면 controller 가 GitHub API 를 호출해 이 scale set 이 속할 runner group 을 조회하고, Actions Service 에서 runner scale set 을 조회하거나 새로 만든다. 그다음 listener pod 를 실행한다.

listener 는 Actions Service 에 인증한 뒤 HTTPS 롱 폴링(long poll) 연결을 연다. 이후 Job Available 메시지가 올 때까지 대기한다. 이 시점에 runner pod 는 하나도 없어도 된다.

스케일업#

저장소에서 workflow 가 실행되면 Actions Service 는 job 마다 runs-on 값과 일치하는 runner 나 scale set 을 찾아 배정한다. scale set 은 설치 이름(runnerScaleSetName)으로 지정하거나, chart 의 scaleSetLabels 로 붙인 label 로 지정한다.

listener 는 Job Available 메시지를 받으면 자신이 감당할 수 있는 만큼 job 을 가져간다. 그리고 Kubernetes API 로 EphemeralRunnerSet 의 replicas 를 원하는 값으로 변경(patch)한다. listener pod 는 이 변경을 위해 전용 Service Account 와 Role 을 쓴다. 메시지 확인(ack)은 이 처리가 성공한 뒤에 보내므로, 처리 중 실패하면 같은 메시지를 다시 처리할 수 있다.

replicas 가 늘면 EphemeralRunner 가 생기고, controller 는 Actions Service 에 JIT(just-in-time) 설정 토큰을 요청한 뒤 runner pod 를 만든다. pod 가 failed 상태가 되면 controller 는 최대 5회까지 다시 만든다. 어떤 runner 도 job 을 받지 못하면 Actions Service 가 24시간 뒤 job 배정을 해제한다.

실행#

runner pod 안의 runner 애플리케이션은 JIT 토큰으로 Actions Service 에 자신을 등록한다. 그리고 listener 와는 별개의 롱 폴링 연결을 열어 job 상세를 받는다. 실행 중에는 로그와 상태를 Actions Service 로 계속 보낸다.

runner 등록에는 이 JIT 토큰만 쓰인다. ARC 가 GitHub API 인증에 쓰는 PAT(personal access token)나 GitHub App 토큰은 runner pod 로 전달되지 않는다. ARC 문서는 이를 legacy 모드 대비 개선점으로 든다. workflow 코드가 실행되는 pod 에 ARC 의 자격 증명이 없다.

정리#

job 이 성공적으로 끝나면 controller 가 Actions Service 에 이 runner 를 삭제해도 되는지 확인하고, EphemeralRunnerSet 이 runner 를 삭제한다. runner 하나는 job 하나만 실행하므로, 다음 job 은 새로 만든 runner pod 에서 시작한다.

스케일 계산#

스케일업 구간에서 listener 가 정하는 목표 runner 수는 minRunners 에 현재 배정된 job 수를 더한 값이고, maxRunners 가 상한이다.

  • 둘 다 지정하지 않으면 job 수만큼 늘고, job 이 없으면 0까지 줄어든다
  • minRunners 를 두면 job 이 없어도 그 수만큼 runner 가 대기한다. 대신 그 pod 들이 자원을 계속 점유한다
  • minRunners 는 maxRunners 를 넘을 수 없다

스케일 신호는 listener 가 받는 메시지에서 나온다. ARC 가 GitHub API 를 주기적으로 조회해 목표 수를 계산하지 않는다.

legacy 모드와의 차이#

ARC 에는 actions.summerwind.dev API 그룹을 쓰는 이전 모드가 있고, 지금은 legacy 모드로 부른다. RunnerDeployment·RunnerSet 으로 runner 를 정의하고 HorizontalRunnerAutoscaler 로 스케일한다. runner scale set 모드가 2023년 정식 출시(GA)된 뒤 GitHub 은 새 모드만 지원하고, legacy 모드는 커뮤니티가 유지한다고 공지했다.

항목legacy 모드runner scale set 모드
스케일 신호GitHub API 주기 조회, 또는 workflow_job webhooklistener 의 롱 폴링 메시지
runner 등록PAT 또는 GitHub App 토큰이 runner pod 로 전달controller 가 받은 JIT 토큰
선행 조건cert-manager 필요cert-manager 불필요
지원 주체커뮤니티GitHub

조회 방식은 TotalNumberOfQueuedAndInProgressWorkflowRuns, PercentageRunnersBusy 같은 지표를 동기화 주기마다 GitHub API 로 계산한다. legacy 문서는 동기화 주기를 짧게 잡을수록 API rate limit 이 빨리 소진된다고 경고한다.

webhook 방식은 별도 webhook 서버가 workflow_job 이벤트를 받아 스케일한다. 대신 GitHub 이 보내는 webhook 이 클러스터 안의 그 서버에 도달해야 한다.

runner scale set 모드는 listener 가 GitHub 으로 아웃바운드 연결을 여는 방식이라, 클러스터로 들어오는 경로가 필요 없다.

containerMode#

workflow 가 container: job 이나 services:, 컨테이너 기반 action 을 쓰면 runner 가 컨테이너를 실행할 수단이 필요하다. gha-runner-scale-set chart 의 containerMode 가 그 방식을 정한다.

  • dind(Docker-in-Docker): runner pod 에 docker:dind 컨테이너를 함께 두고 runner 가 그 Docker daemon 을 쓴다. Docker daemon 은 privileged 모드가 필요하다
  • kubernetes: runner container hooks 가 job 컨테이너를 같은 namespace 의 별도 pod 로 만든다. runner pod 와 job pod 가 작업 디렉터리를 공유하도록 persistent volume 이 필요하다
  • kubernetes-novolume: kubernetes 와 같이 별도 pod 를 만들되, 컨테이너 lifecycle hook 으로 파일시스템을 복원하고 내보내 공유 볼륨 없이 동작한다

containerMode 를 비우고 template 에 pod spec 을 직접 적으면 구성을 원하는 대로 바꿀 수 있다. 아래 선택 기준은 각 모드의 요구 사항에서 정리했다.

dind 가 적합한 경우:

  • workflow 가 docker build·docker run 을 직접 실행한다
  • 클러스터에서 privileged 컨테이너를 허용할 수 있다
  • persistent volume 을 따로 준비하지 않는다

kubernetes 계열이 적합한 경우:

  • privileged 컨테이너를 허용하지 않는다
  • job 이 container: 로 실행 환경을 명시한다
  • persistent volume 을 동적으로 프로비저닝할 수 있으면 kubernetes, 공유 스토리지가 없으면 kubernetes-novolume

kubernetes 계열은 container: 가 없는 job 을 기본으로 거부한다. ACTIONS_RUNNER_REQUIRE_JOB_CONTAINER 를 false 로 바꾸면 허용되지만, GitHub 문서는 이때 runner pod 가 pod 생성·secret 조회 같은 Kubernetes API 권한을 갖게 될 수 있다고 경고한다.

운영 이슈#

GitHub 의 ARC 문제 해결 문서에 나오는 문제를 생애주기 구간별로 나누면 확인할 대상이 좁혀진다.

설치: 이름 길이 오류가 난다. ARC 는 생성한 리소스 이름을 다른 리소스의 label 로 쓰기 때문에 이름을 63자로 제한한다. 그래서 설치 이름은 45자, namespace 는 63자를 넘을 수 없다.

준비: listener pod 가 실행되지 않는다. 먼저 controller 로그를 본다. 오류가 없으면 controller 가 Kubernetes API server 에 접근할 수 있는지 확인한다. Istio 처럼 자동 주입되는 sidecar proxy 를 쓴다면 controller 에서 API server 로 가는 트래픽을 허용하도록 설정되어 있는지 본다. listener pod 가 생성되지 않으면 githubConfigSecret·githubConfigUrl 값부터 의심한다.

스케일업: 오래된 runner 이미지에는 job 이 배정되지 않는다. GitHub.com 기준으로 새 runner 버전이 나온 뒤 63일 안에 업데이트하지 않으면 Actions Service 가 그 runner 에 job 을 보내지 않는다. 커스텀 runner 이미지를 쓸 때 놓치기 쉽다고 봤다.

실행 중 취소: runner pod 가 잠깐 더 생긴다. 취소 신호는 runner 에게 먼저 가고 listener 는 다음 poll 에서 받는다. 그 사이 runner pod 가 종료되면 listener 는 원하는 수를 맞추려고 새 runner 를 만들고, 취소 신호를 받은 뒤 다시 줄인다. 일시적인 현상이다.

마무리#

runner scale set 모드에서 job 하나는 두 연결을 따라 runner pod 하나로 실행되고 삭제된다. listener 는 신호를 받아 replicas 만 바꾸고, runner 는 job 을 직접 받아 실행한다. legacy 모드와 달리 API 조회 대신 메시지로 스케일하고, ARC 의 자격 증명 대신 JIT 토큰으로 runner 를 등록한다. 컨테이너 실행 방식은 privileged 허용 여부와 스토리지 구성에 따라 containerMode 로 고른다.
