Rust 소유권과 메모리 해제

2026년 10월 8일 · 약 7분 읽기

  • Drop trait
  • drop 순서
  • 이동된 값

  • drop 이 실행되지 않는 경우

Rust 에는 가비지 컬렉터(GC)가 없다. 값마다 소유자가 하나 있고, 소유자가 스코프를 벗어나는 지점에서 값이 drop 된다. 그 지점은 런타임이 고르지 않고, 소스 코드의 스코프에서 읽을 수 있다.

GC 언어로 서버를 만들 때는 메모리 회수를 런타임에 맡기고, 파일이나 커넥션처럼 바로 닫아야 하는 자원은 Java 의 try-with-resources, Python 의 with, Go 의 defer 로 따로 관리했다. Rust 는 두 가지를 같은 규칙으로 처리한다. 그 규칙이 정확히 언제 무엇을 실행하는지 정리하고 싶었다. 아래 예제는 모두 rustc 1.94.1, edition 2021 에서 컴파일하고 실행했다.

소유자와 스코프#

String 은 문자열 데이터를 힙에 할당한다.

fn main() {
    {
        let greeting = String::from("hello");
        println!("{greeting}");
    } // greeting 의 스코프가 끝나며 힙 버퍼 해제
}

greeting 은 이 String 의 소유자다. 내부 블록이 끝나면 greeting 의 스코프도 끝나고, 컴파일러가 그 지점에 넣은 drop 이 실행되어 힙 버퍼가 해제된다. The Rust Programming Language 는 이 규칙을 세 문장으로 정리한다.

  • 각 값에는 소유자가 있다
  • 소유자는 한 번에 하나뿐이다
  • 소유자가 스코프를 벗어나면 값이 drop 된다

소유자가 하나뿐이므로 값마다 drop 이 실행될 지점도 하나로 정해진다. 같은 버퍼를 두 번 해제하는 일이 안전한 코드에서는 생기지 않는다.

Drop trait#

값이 drop 될 때 실행할 코드는 Drop trait 으로 정의한다. Vec 과 String 은 drop 될 때 힙 버퍼를 해제하고, 직접 만든 타입도 Drop 을 구현하면 같은 시점에 원하는 코드를 실행한다. 아래 예제들은 drop 되는 순간 이름을 출력하는 Connection 타입을 쓴다.

struct Connection {
    name: &'static str,
}

impl Drop for Connection {
    fn drop(&mut self) {
        println!("drop {}", self.name);
    }
}

drop 메서드는 직접 호출할 수 없다.

fn main() {
    let conn = Connection { name: "conn" };
    conn.drop();
}

error[E0040]: explicit use of destructor method
  --> explicit.rs:13:10
   |
13 |     conn.drop();
   |          ^^^^ explicit destructor calls not allowed
   |
help: consider using `drop` function
   |
13 -     conn.drop();
13 +     drop(conn);
   |

직접 호출을 허용하면 스코프 끝에서 자동으로 실행되는 drop 과 겹쳐 같은 값이 두 번 drop 된다. 컴파일러가 제안하는 drop(conn) 은 prelude 에 포함된 std::mem::drop 함수다. 이 함수는 인자의 소유권을 받고 아무 일도 하지 않는다. 함수가 끝나면 매개변수의 스코프가 끝나고, 그 지점에서 Drop::drop 이 실행된다.

fn main() {
    let conn = Connection { name: "conn" };
    drop(conn); // std::mem::drop
    println!("end of main");
}

drop conn
end of main

drop 순서#

한 스코프에 값이 여러 개면 drop 순서가 정해져 있다. 변수 둘, 내부 블록, Connection 필드 둘을 가진 struct 로 순서를 출력해 봤다.

// Connection 은 위와 같다
struct Session {
    conn: Connection,
    cache: Connection,
}

fn main() {
    let _first = Connection { name: "first" };
    let _second = Connection { name: "second" };
    {
        let _inner = Connection { name: "inner" };
        println!("end of inner scope");
    }
    let _session = Session {
        conn: Connection { name: "session.conn" },
        cache: Connection { name: "session.cache" },
    };
    println!("end of main");
}

end of inner scope
drop inner
end of main
drop session.conn
drop session.cache
drop second
drop first

내부 블록이 먼저 끝나므로 _inner 가 처음 drop 된다. main 이 끝날 때는 남은 변수가 선언 역순으로 drop 된다. 마지막에 선언한 _session 이 먼저이고, _first 가 마지막이다. _session 안에서는 필드가 선언 순서대로 conn, cache 순으로 drop 된다. The Rust Reference 는 변수를 선언 역순으로, struct 필드를 선언 순서로 drop 한다고 정의한다. Drop 문서는 이 순서를 언어가 보장한다고 적는다.

변수 이름 앞의 _ 는 사용하지 않는 변수 경고만 끈다. _first 는 일반 변수와 같이 스코프 끝에서 drop 된다. 이름 전체가 _ 인 패턴은 다르게 동작한다.

이동된 값#

값을 함수 인자로 넘기면 소유권이 함수의 매개변수로 이동한다.

// Connection 은 위와 같다
fn close(conn: Connection) {
    println!("close {}", conn.name);
} // 새 소유자 conn 의 스코프가 끝나는 지점

fn main() {
    let _kept = Connection { name: "kept" };
    let handed = Connection { name: "handed" };
    close(handed); // 소유권이 close 로 이동
    println!("end of main");
}

close handed
drop handed
end of main
drop kept

handed 의 drop 은 main 끝이 아니라 close 끝에서 실행됐다. 소유자가 바뀌면 drop 지점도 새 소유자의 스코프 끝으로 옮겨진다. main 이 끝날 때 handed 는 더 이상 값을 갖고 있지 않으므로 drop 되지 않고, _kept 만 drop 된다. Reference 는 이동으로 비워진 변수를 초기화되지 않은 상태로 보고, 초기화되지 않은 변수는 drop 하지 않는다고 정의한다. 이동된 값까지 drop 하면 같은 값이 두 번 drop 된다.

메모리가 아닌 자원#

Drop 은 메모리 해제에만 쓰이지 않는다. 값이 소유한 자원을 그 값이 존재하는 동안만 유지하고 drop 될 때 정리하는 방식을 RAII(Resource Acquisition Is Initialization)라고 부른다. C++ 에서 온 이름이고, 표준 라이브러리의 파일과 lock 이 이 방식으로 동작한다.

std::fs::File 은 drop 될 때 파일을 닫는다.

use std::fs::File;
use std::io::Write;

fn main() -> std::io::Result<()> {
    {
        let mut log = File::create("app.log")?;
        log.write_all(b"started\n")?;
        log.sync_all()?; // 디스크 기록 에러를 drop 전에 받는다
    } // log drop, 파일 닫힘
    println!("{}", std::fs::read_to_string("app.log")?);
    Ok(())
}

File 의 Drop 구현은 닫을 때 생긴 에러를 무시한다. drop 은 값을 반환하지 않으므로 에러를 전달할 수 없다. File 문서는 이 에러를 직접 처리해야 하면 sync_all 을 쓰라고 안내한다. sync_all 은 데이터가 디스크에 기록될 때까지 기다리고, 그 과정의 에러를 Result 로 돌려준다.

Mutex 의 lock 은 MutexGuard 를 돌려주고, guard 가 drop 될 때 lock 이 해제된다. guard 가 살아 있는 동안과 스코프가 끝난 뒤의 lock 상태를 try_lock 으로 확인했다.

use std::sync::Mutex;

fn main() {
    let counter = Mutex::new(0);
    {
        let mut guard = counter.lock().unwrap();
        *guard += 1;
        println!("in scope: locked = {}", counter.try_lock().is_err());
    } // guard drop, lock 해제
    println!("after scope: locked = {}", counter.try_lock().is_err());
}

in scope: locked = true
after scope: locked = false

try_lock 은 이미 잠긴 mutex 에서 기다리지 않고 WouldBlock 에러를 돌려준다. guard 를 소유한 스레드가 lock 을 다시 호출하는 경우는 문서가 동작을 정하지 않는다. panic 이나 deadlock 이 될 수 있다고만 적혀 있으므로, 예제에서는 try_lock 으로 상태만 확인했다.

unlock 을 호출하는 코드는 어디에도 없다. lock 은 guard 의 스코프가 끝날 때까지 유지된다. 더 일찍 해제해야 하면 내부 블록으로 스코프를 줄이거나 drop(guard) 를 호출한다.

guard 를 변수에 담지 않으면 lock 이 바로 해제된다. 이름 전체가 _ 인 패턴은 값을 어떤 변수에도 바인딩하지 않는다. 소유자가 없는 값은 임시 값으로 남고, Reference 에 따라 그 문장이 끝날 때 drop 된다. rustc 는 lock 에 대해 이 실수를 기본으로 거부한다.

let _ = counter.lock().unwrap();

error: non-binding let on a synchronization lock
 --> underscore.rs:6:9
  |
6 |     let _ = counter.lock().unwrap();
  |         ^ this lock is not assigned to a binding and is immediately dropped
  |
  = note: `#[deny(let_underscore_lock)]` (part of `#[deny(let_underscore)]`) on by default
help: consider binding to an unused variable to avoid immediately dropping the value
  |
6 |     let _unused = counter.lock().unwrap();
  |          ++++++

let_underscore_lock lint 는 lock guard 에만 적용된다. 다른 타입은 기본 설정에서 아무 표시 없이 문장 끝에 drop 된다.

// Connection 은 위와 같다
fn main() {
    let _ = Connection { name: "wildcard" };
    let _named = Connection { name: "named" };
    println!("end of main");
}

drop wildcard
end of main
drop named

drop 이 실행되지 않는 경우#

drop 이 항상 실행되지는 않는다.

// Connection 은 위와 같다
fn main() {
    let forgotten = Connection { name: "forgotten" };
    std::mem::forget(forgotten);
    let _conn = Connection { name: "conn" };
    std::process::exit(0);
}

이 프로그램은 아무것도 출력하지 않는다. std::mem::forget 은 값의 소유권을 받은 뒤 소멸자를 실행하지 않는다. std::process::exit 은 어느 스레드의 스택에 남은 값도 drop 하지 않고 프로세스를 끝낸다.

문서는 forget 이 unsafe 가 아닌 이유로, Rust 의 안전성 보장에 소멸자(destructor)가 항상 실행된다는 약속이 포함되지 않는다는 점을 든다. drop 은 정상 흐름에서 자원 정리를 보장하는 장치로 보는 쪽이 맞다고 판단했다. 프로세스가 어떻게 끝나든 반드시 남겨야 하는 기록이라면 drop 에만 맡기지 않는 편이 낫다고 봤다.

마무리#

Rust 는 값마다 소유자를 하나 두고, 소유자의 스코프가 끝나는 지점에서 값을 drop 한다. 변수는 선언 역순으로, 필드는 선언 순서로 drop 되고, 이동된 값은 새 소유자의 스코프 끝에서 한 번만 drop 된다. 이 규칙이 힙 버퍼, 파일, mutex lock 에 같이 적용되므로, 정상 흐름에서는 해제 코드를 따로 쓰지 않는다. 닫을 때의 에러를 받아야 하거나 forget·exit 처럼 drop 을 건너뛰는 경로가 있을 때만 직접 처리한다. GC 언어에서는 런타임이 메모리 회수 시점을 정하고, 다른 자원은 defer·with 로 따로 정리한다. Rust 에서는 둘 다 소유자의 스코프를 따른다.
