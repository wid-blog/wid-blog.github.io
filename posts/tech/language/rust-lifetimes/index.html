Rust 라이프타임

Rust 의 라이프타임 표기 'a 는 값을 더 오래 살리지 않는다. 함수가 돌려주는 참조가 어느 입력에서 빌려 온 것인지를 시그니처에 적는 표기다. borrow checker 는 이 표기와 각 참조가 마지막으로 쓰이는 지점을 보고 대여가 유효한 구간을 계산한다.

컴파일러가 제안하는 대로 'a 를 붙이면 대부분 컴파일은 된다. 그 제안이 호출하는 쪽에 무엇을 요구하는지, 표기를 생략해도 되는 경우는 어떤 규칙으로 정해지는지 정리하고 싶었다. 아래 예제는 모두 rustc 1.94.1, edition 2021 에서 컴파일하고 실행했다.

대여 구간#

벡터의 첫 원소를 빌린 뒤 벡터에 원소를 추가하는 코드다.

fn main() {
    let mut scores = vec![10, 20, 30];
    let first = &scores[0];
    scores.push(40);
    println!("first = {first}");
}

컴파일러는 이 코드를 거부한다.

error[E0502]: cannot borrow `scores` as mutable because it is also borrowed as immutable
 --> nll_err.rs:4:5
  |
3 |     let first = &scores[0];
  |                  ------ immutable borrow occurs here
4 |     scores.push(40);
  |     ^^^^^^^^^^^^^^^ mutable borrow occurs here
5 |     println!("first = {first}");
  |                        ----- immutable borrow later used here

push 는 벡터의 버퍼를 새로 할당할 수 있다. 그러면 first 가 가리키던 메모리가 해제되므로, 불변 대여가 살아 있는 동안 가변 대여를 허용하지 않는다. 에러 메시지의 세 번째 표시 later used here 가 판단 근거다. first 가 5행에서 다시 쓰이기 때문에 3행의 대여가 5행까지 이어진다.

println! 을 push 앞으로 옮기면 컴파일된다.

fn main() {
    let mut scores = vec![10, 20, 30];
    let first = &scores[0];
    println!("first = {first}");
    scores.push(40); // first 는 위 println 이 마지막 사용
    println!("len = {}", scores.len());
}

first 라는 변수는 main 끝까지 스코프에 남아 있다. 그래도 대여는 마지막 사용인 println! 에서 끝나고, push 와 겹치지 않는다. 예외도 있다. 참조를 든 값의 타입이 Drop 을 구현하면 스코프 끝에서 실행되는 drop 도 사용으로 계산되어, 대여가 스코프 끝까지 이어진다.

대여 구간을 변수 스코프가 아니라 사용 지점으로 계산하는 방식이 NLL(non-lexical lifetimes)이다. Rust 1.31 에서 2018 edition 에 먼저 들어왔고, 1.36 에서 2015 edition 에도 적용됐다. 1.63 에서는 스코프 기준으로 검사하던 이전 borrow checker 가 rustc 에서 제거됐다. 1.63 이후의 rustc 는 모든 edition 에서 대여 구간을 이 방식으로 계산한다.

반환 참조의 출처#

함수 안에서는 컴파일러가 모든 사용 지점을 볼 수 있다. 함수 경계를 넘으면 사정이 다르다. 호출하는 쪽은 함수 본문을 보지 않고 시그니처만으로 반환값이 무엇을 빌리고 있는지 판단해야 한다.

경로에서 루트 디렉터리 접두사를 떼는 함수를 라이프타임 표기 없이 쓰면 컴파일되지 않는다.

fn strip_root(path: &str, root: &str) -> &str {
    path.strip_prefix(root).unwrap_or(path)
}

error[E0106]: missing lifetime specifier
 --> strip_elide.rs:1:42
  |
1 | fn strip_root(path: &str, root: &str) -> &str {
  |                     ----        ----     ^ expected named lifetime parameter
  |
  = help: this function's return type contains a borrowed value, but the signature does not say whether it is borrowed from `path` or `root`
help: consider introducing a named lifetime parameter
  |
1 | fn strip_root<'a>(path: &'a str, root: &'a str) -> &'a str {
  |              ++++        ++             ++          ++

help 는 반환값이 path 에서 왔는지 root 에서 왔는지 시그니처에 적혀 있지 않다고 설명한다. 컴파일러는 둘 다 'a 로 묶는 시그니처를 제안한다. 그대로 받아들이면 이 함수는 컴파일되지만, 호출하는 쪽에서 거부되는 코드가 생긴다.

fn strip_root<'a>(path: &'a str, root: &'a str) -> &'a str {
    path.strip_prefix(root).unwrap_or(path)
}

fn main() {
    let path = String::from("/srv/app/config.toml");
    let relative;
    {
        let root = String::from("/srv/app/");
        relative = strip_root(&path, &root);
    } // root 해제
    println!("{relative}");
}

error[E0597]: `root` does not live long enough
  --> strip_err.rs:10:38
   |
 9 |         let root = String::from("/srv/app/");
   |             ---- binding `root` declared here
10 |         relative = strip_root(&path, &root);
   |                                      ^^^^^ borrowed value does not live long enough
11 |     } // root 해제
   |     - `root` dropped here while still borrowed
12 |     println!("{relative}");
   |                -------- borrow later used here

반환값은 실제로 path 의 일부만 가리킨다. 하지만 시그니처가 “반환값은 path 와 root 가 모두 살아 있는 동안만 유효하다"고 적었으므로, 컴파일러는 root 가 해제된 뒤 relative 를 쓰는 것을 거부한다. 호출하는 쪽의 컴파일러는 본문이 아니라 시그니처를 기준으로 검사한다.

반환값의 실제 출처인 path 에만 'a 를 붙이면 같은 호출이 컴파일된다. 표기를 생략한 root 에는 다음 절의 1번 규칙에 따라 별개의 라이프타임이 붙는다.

fn strip_root<'a>(path: &'a str, root: &str) -> &'a str {
    path.strip_prefix(root).unwrap_or(path)
}

이 계약은 함수 본문에도 적용된다. 같은 시그니처에서 root 를 반환하도록 바꾸면 이번에는 함수 정의가 거부된다.

fn strip_root<'a>(path: &'a str, root: &str) -> &'a str {
    if path.starts_with(root) { root } else { path }
}

error[E0621]: explicit lifetime required in the type of `root`
 --> strip_body_err.rs:2:33
  |
2 |     if path.starts_with(root) { root } else { path }
  |                                 ^^^^ lifetime `'a` required

시그니처 하나로 검사가 두 번 이뤄진다. 본문은 시그니처가 약속한 출처만 반환하는지 검사받는다. 호출하는 쪽은 시그니처가 요구하는 만큼 입력을 살려 두는지 검사받는다. 같은 'a 로 묶는 입력이 많을수록 호출하는 쪽이 지켜야 할 조건이 늘어난다. 그래서 컴파일러 제안은 출발점으로 보고, 반환값이 빌릴 수 있는 입력에만 'a 를 붙이는 쪽이 맞다고 판단했다. root 를 반환할 수도 있는 함수라면 두 입력을 모두 'a 로 묶는 제안이 맞는 시그니처다.

표기를 생략하는 규칙#

참조를 받아 참조를 돌려주는 함수가 모두 'a 를 요구하지는 않는다. 다음 함수는 표기 없이 컴파일된다.

fn file_name(path: &str) -> &str {
    path.rsplit('/').next().unwrap_or(path)
}

The Rust Reference 는 라이프타임을 생략했을 때 컴파일러가 채워 넣는 규칙을 이렇게 정한다.

  1. 매개변수에서 생략된 라이프타임은 각각 별개의 라이프타임 매개변수가 된다
  2. 매개변수에 쓰인 라이프타임이 정확히 하나면, 생략된 출력 라이프타임은 모두 그것이 된다
  3. 메서드의 receiver 가 &self 나 &mut self 면, 생략된 출력 라이프타임은 모두 self 참조의 라이프타임이 된다

file_name 은 입력 참조가 하나라서 2번 규칙으로 fn file_name<'a>(path: &'a str) -> &'a str 이 된다. strip_root 는 1번 규칙으로 입력 두 개에 서로 다른 라이프타임이 붙고, 2번과 3번이 모두 적용되지 않아 출력 라이프타임을 정할 수 없다. Reference 는 이 경우를 에러로 정의하고, 앞에서 본 E0106 이 그 에러다.

시그니처적용 규칙결과
fn file_name(&str) -> &str1, 2출력 = 유일한 입력
fn strip_root(&str, &str) -> &str1출력을 정할 수 없음 (E0106)
fn get(&self, &str) -> &str1, 3출력 = self 참조

3번 규칙은 흔한 메서드에서 의도한 결과를 낸다. 다만 참조를 필드로 가진 struct 에서는 원하는 결과가 아닐 수 있다.

참조를 필드로 가진 struct#

HTTP 요청 줄을 공백 단위로 잘라 토큰을 돌려주는 struct 다. 입력 문자열을 복사하지 않고 &str 로 빌려 들고 있으므로, struct 에 라이프타임 매개변수 'a 가 붙는다. Tokens<'a> 는 “이 값은 'a 동안 유효한 문자열을 빌리고 있다"는 뜻이다.

struct Tokens<'a> {
    rest: &'a str,
}

impl<'a> Tokens<'a> {
    fn next_token(&mut self) -> Option<&str> {
        let trimmed = self.rest.trim_start();
        if trimmed.is_empty() {
            return None;
        }
        let end = trimmed.find(' ').unwrap_or(trimmed.len());
        let (token, rest) = trimmed.split_at(end);
        self.rest = rest;
        Some(token)
    }
}

fn main() {
    let line = String::from("GET /health HTTP/1.1");
    let mut tokens = Tokens { rest: &line };
    let method = tokens.next_token();
    let path = tokens.next_token();
    println!("{method:?} {path:?}");
}

토큰 두 개를 차례로 꺼내 함께 쓰는 이 코드는 컴파일되지 않는다.

error[E0499]: cannot borrow `tokens` as mutable more than once at a time
  --> parser_err.rs:22:16
   |
21 |     let method = tokens.next_token();
   |                  ------ first mutable borrow occurs here
22 |     let path = tokens.next_token();
   |                ^^^^^^ second mutable borrow occurs here
23 |     println!("{method:?} {path:?}");
   |                ------ first borrow later used here

next_token 의 반환 타입 Option<&str> 은 라이프타임이 생략됐고, 3번 규칙에 따라 &mut self 의 라이프타임을 받는다. 그래서 method 는 line 이 아니라 tokens 의 가변 대여에서 나온 값이 된다. method 가 23행까지 쓰이니 첫 가변 대여도 23행까지 이어지고, 22행의 두 번째 next_token 호출과 겹친다.

토큰은 실제로 line 의 일부다. 반환 타입에 struct 의 'a 를 직접 적으면 시그니처가 그 사실과 일치한다.

    fn next_token(&mut self) -> Option<&'a str> {

Some("GET") Some("/health")

이제 &mut self 대여는 next_token 호출이 끝나면 함께 끝난다. method 와 path 는 line 만 빌리므로, line 이 살아 있는 동안 자유롭게 쓸 수 있다.

참조를 든 struct 의 메서드가 참조를 돌려줄 때는 그 참조가 struct 자체에서 왔는지, struct 가 빌린 원본에서 왔는지를 먼저 확인하는 쪽이 맞다고 봤다. 원본에서 왔는데 생략 규칙에 맡기면 반환값이 struct 의 대여에 묶인다.

참조 타입의 'static 과 bound 의 'static#

'static 은 프로그램 전체 구간이라는 하나의 라이프타임이다. 다만 참조 타입에 붙을 때와 타입 매개변수의 bound 로 붙을 때 요구하는 조건이 다르다.

참조 타입에 붙은 &'static str 은 프로그램이 끝날 때까지 유효한 참조다. 문자열 리터럴이 대표적인 예로, 바이너리에 포함되어 해제되지 않는다.

trait bound 로 쓰인 T: 'static 은 다르다. Rust by Example 은 이를 “타입이 'static 이 아닌 참조를 포함하지 않는다"로 정의한다. 값이 프로그램 끝까지 살아야 한다는 뜻이 아니다. 런타임에 만든 String 처럼 참조를 들지 않고 데이터를 소유한 값은 이 bound 를 항상 만족한다.

use std::fmt::Debug;
use std::thread;

fn log_later<T: Debug + Send + 'static>(value: T) -> thread::JoinHandle<()> {
    thread::spawn(move || println!("{value:?}"))
}

fn main() {
    let name = String::from("worker-1"); // 런타임에 만든 String
    log_later(name).join().unwrap();

    let label: &'static str = "literal"; // 바이너리에 들어가는 문자열
    log_later(label).join().unwrap();
}

"worker-1"
"literal"

name 은 main 에서 만든 지역 값인데도 'static bound 를 통과한다. 소유권이 새 스레드로 넘어가므로 빌린 데이터가 남지 않기 때문이다. 반대로 &name 을 넘기면 거부된다.

// use 선언과 log_later 는 위 예제와 같다
fn main() {
    let name = String::from("worker-1");
    log_later(&name).join().unwrap();
}

error[E0597]: `name` does not live long enough
  --> static_err.rs:10:15
   |
 9 |     let name = String::from("worker-1");
   |         ---- binding `name` declared here
10 |     log_later(&name).join().unwrap();
   |     ----------^^^^^-
   |     |         |
   |     |         borrowed value does not live long enough
   |     argument requires that `name` is borrowed for `'static`
11 | }
   | - `name` dropped here while still borrowed

log_later 의 bound 는 std::thread::spawn 의 시그니처 F: FnOnce() -> T + Send + 'static 에서 왔다. 새 스레드가 언제 끝날지 컴파일러가 알 수 없으므로, 스레드에 넘기는 값은 'static 이 아닌 참조를 포함하지 않아야 한다. 앞의 label 처럼 &'static str 은 참조여도 통과한다.

스레드가 끝나는 시점을 코드로 보장할 수 있으면 지역 값을 빌려줄 수 있다. Rust 1.63 에서 안정화된 std::thread::scope 는 스코프 안에서 띄운 스레드를 스코프가 끝나기 전에 모두 join 한다.

use std::thread;

fn main() {
    let name = String::from("worker-1");
    thread::scope(|s| {
        s.spawn(|| println!("{name}"));
    }); // scope 가 끝나기 전에 모든 스레드가 join 된다
    println!("still own {name}");
}

worker-1
still own worker-1

스레드가 name 보다 먼저 끝난다는 보장이 생기므로 'static 이 필요 없다. 스레드가 name 을 빌리기만 하므로 스코프가 끝난 뒤에도 main 이 name 을 계속 소유한다.

마무리#

borrow checker 는 함수 안에서는 각 참조가 다시 쓰이는 지점으로 대여 구간을 계산한다. 함수 경계에서는 시그니처의 라이프타임 표기를 계약으로 삼아 본문과 호출하는 쪽을 따로 검사한다. 생략 규칙은 흔한 시그니처에서 그 계약을 대신 적어 주지만, 참조를 든 struct 의 메서드처럼 규칙이 고른 계약이 실제 출처와 다를 때는 'a 를 직접 적어야 한다. T: 'static 같은 bound 도 값을 오래 살리라는 요구가 아니라, 빌린 참조가 남지 않았는지 확인하는 조건이다. 어느 경우든 표기를 고치면 값이 살아 있는 기간은 그대로이고, 컴파일러가 확인하는 조건이 바뀐다.
