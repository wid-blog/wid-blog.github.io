Rust 클로저와 iterator

Rust 의 클로저는 주변 변수를 캡처하는 익명 함수다. 컴파일러는 클로저마다 캡처한 값을 필드로 가진 struct 에 가까운 익명 타입을 만든다. 본문이 캡처한 값을 읽기만 하면 공유 참조를, 바꾸면 가변 참조를, 소비하면 값 자체를 필드로 둔다. 본문이 그 값으로 하는 일에 따라 클로저가 Fn·FnMut·FnOnce 중 무엇을 구현하는지도 정해진다. iterator 어댑터 map·filter 는 이런 클로저를 받아 struct 로 감쌀 뿐이고, 실제 계산은 collect 같은 메서드가 next 를 부를 때 일어난다.

캡처 방식은 클로저 크기로, 지연 평가는 println! 이 찍히는 순서로 확인했다. 아래 예제는 모두 rustc 1.94.1, edition 2021 에서 컴파일하고 aarch64-apple-darwin(Apple Silicon macOS)에서 실행했다. 크기는 64비트 타깃 기준이다.

캡처 방식 — 공유 참조, 가변 참조, 값#

클로저 넷을 만들고 size_of_val 로 크기를 쟀다.

use std::mem::size_of_val;

fn main() {
    let name = String::from("wid");
    let mut count = 0;

    let nothing = || println!("hello");
    let read = || println!("{name}");
    let mut bump = || count += 1;

    println!("nothing = {} bytes", size_of_val(&nothing));
    println!("read    = {} bytes", size_of_val(&read));
    println!("bump    = {} bytes", size_of_val(&bump));

    nothing();
    read();
    bump();
    bump();
    println!("count = {count}");

    let consume = || drop(name);
    println!("consume = {} bytes", size_of_val(&consume));
    consume();
}

nothing = 0 bytes
read    = 8 bytes
bump    = 8 bytes
hello
wid
count = 2
consume = 24 bytes

아무것도 캡처하지 않은 nothing 은 0바이트다. read 와 bump 는 포인터 하나 크기인 8바이트로, 각각 &String 과 &mut i32 를 담았다. consume 은 String 자체(포인터·길이·용량)를 담아 24바이트다. 본문의 drop(name) 이 소유권을 가져가야 하기 때문이다.

The Rust Reference 는 캡처 방식을 불변 참조(이 글의 공유 참조), 가변 참조, 이동 순으로 나열하고(사이에 고유 불변 참조라는 특수한 방식이 하나 더 있다), 본문에서 값을 쓰는 방식과 맞는 첫 방식을 고른다고 적는다. 필요한 만큼만 빌린다.

가변 참조로 캡처한 클로저가 마지막으로 쓰이기 전까지는 원래 변수를 읽을 수 없다. 참조와 borrow 글의 대여 규칙이 클로저 필드에도 적용된다.

fn main() {
    let mut count = 0;
    let mut bump = || count += 1;
    println!("{count}");
    bump();
}

move — 본문과 관계없이 값으로#

move 를 붙이면 본문이 읽기만 해도 캡처한 변수를 값으로 가져간다.

use std::mem::size_of_val;

fn main() {
    let name = String::from("wid");
    let id = 7;

    let by_ref = || println!("{name} {id}");
    println!("by_ref  = {} bytes", size_of_val(&by_ref));
    by_ref();

    let by_move = move || println!("{name} {id}");
    println!("by_move = {} bytes", size_of_val(&by_move));
    by_move();
    by_move();
    println!("id = {id}");
}

by_ref  = 16 bytes
wid 7
by_move = 32 bytes
wid 7
wid 7
id = 7

본문은 같은데 by_ref 는 참조 두 개로 16바이트, by_move 는 String 24바이트와 i32 4바이트에 정렬용 패딩이 붙어 32바이트다. 필드 순서는 측정하지 않았고, 그림의 배치는 크기만 맞춘 것이다. id 는 Copy 라 클로저에 복사본이 들어가고, main 에서도 계속 쓸 수 있다. String 인 name 은 이동했으므로 move 클로저를 만든 뒤에 쓰면 E0382 가 난다.

move 가 꼭 필요한 곳은 클로저가 캡처한 변수보다 오래 살아야 할 때다. 함수가 클로저를 반환하면 함수의 지역 변수는 반환 시점에 사라지므로, 참조로 캡처한 클로저는 돌려줄 수 없다.

fn make_adder(n: i32) -> impl Fn(i32) -> i32 {
    |x| x + n
}

fn main() {
    let add5 = make_adder(5);
    println!("{}", add5(1));
}

Fn, FnMut, FnOnce — 캡처한 값으로 하는 일#

클로저를 인자로 받는 함수는 세 trait 중 하나를 bound 로 건다. 차이는 호출할 때 클로저 자신을 어떻게 받는지다. Fn 은 &self, FnMut 는 &mut self, FnOnce 는 self 로 받는다. 그래서 FnOnce 로 부른 클로저는 그 호출로 소비된다.

어느 trait 를 구현할지는 본문이 정한다. Reference 의 Call traits 절에 따르면 모든 클로저는 FnOnce 를 구현하고, 캡처한 값을 밖으로 옮기지 않으면 FnMut 를, 바꾸지도 않으면 Fn 까지 구현한다. std 에서도 Fn 은 FnMut 를, FnMut 는 FnOnce 를 supertrait 로 선언한다. Fn 클로저는 FnMut·FnOnce bound 자리에도, FnMut 클로저는 FnOnce 자리에도 넘길 수 있다.

fn call_twice<F: Fn()>(f: F) {
    f();
    f();
}

fn call_twice_mut<F: FnMut()>(mut f: F) {
    f();
    f();
}

fn call_once<F: FnOnce()>(f: F) {
    f();
}

fn main() {
    let name = String::from("wid");
    let mut count = 0;

    call_twice(|| println!("read {name}"));
    call_twice_mut(|| count += 1);
    println!("count = {count}");

    call_once(|| println!("read {name}"));
    call_once(move || drop(name));
}

read wid
read wid
count = 2
read wid

읽기만 하는 클로저는 Fn 이라 call_once 에도 넘어간다. 반대 방향은 거부된다. 값을 바꾸는 FnMut 클로저를 Fn 자리에 넘긴 경우다.

fn call_twice<F: Fn()>(f: F) {
    f();
    f();
}

fn main() {
    let mut count = 0;
    call_twice(|| count += 1);
}

move 와 FnOnce 는 별개다. move 는 캡처하는 방식을, Fn 계열은 본문이 캡처한 값으로 하는 일을 정한다. Reference 도 move 클로저가 여전히 Fn 이나 FnMut 일 수 있다고 적는다. 일반 함수도 시그니처가 맞으면 Fn bound 에 넘길 수 있다.

fn call_twice<F: Fn()>(f: F) {
    f();
    f();
}

fn double(x: i32) -> i32 {
    x * 2
}

fn apply<F: Fn(i32) -> i32>(f: F, x: i32) -> i32 {
    f(x)
}

fn main() {
    let name = String::from("wid");
    call_twice(move || println!("moved {name}"));

    let offset = 10;
    println!("{}", apply(double, 1));
    println!("{}", apply(|x| x + offset, 1));
}

moved wid
2
11

name 을 값으로 가져간 move 클로저가 call_twice 에서 두 번 불렸다. 본문이 name 을 읽기만 하므로 Fn 이다. 함수가 클로저를 받을 때는 가장 넓은 FnOnce 부터 생각하고, 여러 번 불러야 하면 FnMut, 공유 참조로 불러야 하면 Fn 으로 좁히는 순서가 호출하는 쪽에 거는 제약을 최소로 둔다고 봤다. 제네릭 bound 와 impl Trait 자체는 trait·제네릭·dyn 글에서 다뤘다.

Iterator trait 와 next#

iterator 는 Iterator trait 를 구현한 타입이다. 필수 메서드는 하나다.

fn next(&mut self) -> Option<Self::Item>;

next 는 원소가 남아 있으면 Some, 끝나면 None 을 돌려준다. &mut self 로 받는 이유는 부를 때마다 내부 위치가 바뀌기 때문이다. 직접 구현해 보면 for 가 결국 next 를 반복해서 부르는 구조라는 점이 드러난다.

struct Countdown {
    remaining: u32,
}

impl Iterator for Countdown {
    type Item = u32;

    fn next(&mut self) -> Option<u32> {
        if self.remaining == 0 {
            return None;
        }
        self.remaining -= 1;
        Some(self.remaining + 1)
    }
}

fn main() {
    let mut countdown = Countdown { remaining: 2 };
    println!("{:?}", countdown.next());
    println!("{:?}", countdown.next());
    println!("{:?}", countdown.next());

    for n in (Countdown { remaining: 3 }) {
        print!("{n} ");
    }
    println!();
}

Some(2)
Some(1)
None
3 2 1

next 하나만 구현했는데 for 로 돌릴 수 있다. map·filter·collect 같은 나머지 메서드는 Iterator trait 의 기본 메서드라 Countdown 에서도 그대로 쓸 수 있다.

iter, iter_mut, into_iter — 원소를 어떻게 꺼내는가#

Vec 에서 iterator 를 얻는 메서드는 셋이고, 셋이 내는 Item 타입 이름을 type_name 으로 출력했다.

fn item_type<I: Iterator>(_: &I) -> &'static str {
    std::any::type_name::<I::Item>()
}

fn main() {
    let mut names = vec![String::from("a"), String::from("b")];

    println!("iter      -> {}", item_type(&names.iter()));
    println!("iter_mut  -> {}", item_type(&names.iter_mut()));

    for name in names.iter_mut() {
        name.push('!');
    }
    for name in names.iter() {
        print!("{name} ");
    }
    println!();

    let owned = names.into_iter();
    println!("into_iter -> {}", item_type(&owned));
    let joined: Vec<String> = owned.collect();
    println!("{joined:?}");
}

iter      -> &alloc::string::String
iter_mut  -> &mut alloc::string::String
a! b!
into_iter -> alloc::string::String
["a!", "b!"]

iter 는 &String 을 꺼내 읽기만 하고, iter_mut 는 &mut String 을 꺼내 원소를 제자리에서 바꾼다. 두 경우 names 는 그대로 남는다. into_iter 는 self 를 받아 Vec 을 소비하고 String 값 자체를 꺼낸다. for 는 IntoIterator::into_iter 로 iterator 를 얻는데, for x in &names, for x in &mut names, for x in names 는 각각 iter·iter_mut·into_iter 와 같은 Item 을 내는 iterator 를 만든다. 마지막 형태는 names 를 이동시키므로 반복문 뒤에서 쓸 수 없다.

fn main() {
    let names = vec![String::from("a"), String::from("b")];
    for name in names {
        println!("{name}");
    }
    println!("{}", names.len());
}

어댑터는 지연 평가된다#

map·filter·take 처럼 iterator 를 받아 iterator 를 돌려주는 메서드를 어댑터라고 한다. 어댑터는 호출 시점에 아무것도 계산하지 않는다. map 만 부르고 결과를 쓰지 않으면 클로저 안의 println! 은 한 번도 실행되지 않고 경고가 나온다.

fn main() {
    let numbers = vec![1, 2, 3];
    numbers.iter().map(|n| {
        println!("map {n}");
        n * 10
    });
    println!("done");
}

Map struct 에 붙은 #[must_use = "iterators are lazy and do nothing unless consumed"] 가 이 경고를 낸다. 실행 결과에는 done 만 찍혔다.

계산은 collect·sum·for 처럼 iterator 를 소비하는 쪽이 next 를 부를 때 일어난다. 맨 끝의 소비자가 바로 앞 어댑터의 next 를 부르고, 그 어댑터가 다시 앞의 next 를 부르는 식이다. std 의 sum 같은 메서드는 fold 로 구현해 next 를 직접 부르지 않기도 하지만, 원소가 하나씩 체인을 지나는 순서는 같다. 원소마다 어느 단계를 지나는지 보려고 map 과 filter 에 println! 을 넣었다.

fn main() {
    let numbers = vec![1, 2, 3, 4];
    let picked: Vec<i32> = numbers
        .iter()
        .map(|n| {
            println!("map    {n}");
            n * 10
        })
        .filter(|n| {
            println!("filter {n}");
            n % 20 == 0
        })
        .take(1)
        .collect();
    println!("picked = {picked:?}");
}

map    1
filter 10
map    2
filter 20
picked = [20]

map 이 네 원소를 먼저 다 처리하고 filter 가 이어받는 순서가 아니다. 1 이 map 과 filter 를 지나 버려진 뒤에야 2 를 꺼냈다. 20 이 take(1) 을 채우자 take 는 다음 next 에서 앞 단계를 부르지 않고 바로 None 을 돌려줬다. 그래서 3 과 4 는 map 에 들어가지도 않았다. 중간 Vec 이 만들어지지 않고, 필요한 원소까지만 계산된다.

map 의 시그니처를 보면 어댑터가 클로저에 거는 bound 가 보인다.

fn map<B, F>(self, f: F) -> Map<Self, F>
where
    Self: Sized,
    F: FnMut(Self::Item) -> B,

map 은 원소마다 클로저를 부르므로 FnOnce 로는 안 되고, 클로저가 상태를 바꿔도 되도록 Fn 대신 FnMut 를 요구한다. 그래서 캡처한 변수를 바꾸는 클로저도 넘길 수 있다.

fn main() {
    let words = vec!["fig", "apple", "banana"];
    let mut calls = 0;
    let lengths: Vec<usize> = words
        .iter()
        .map(|w| {
            calls += 1;
            w.len()
        })
        .collect();
    println!("{lengths:?}, calls = {calls}");
}

[3, 5, 6], calls = 3

어댑터 체인은 클로저를 가진 struct#

어댑터가 계산을 미룰 수 있는 것은 앞 iterator 와 클로저를 필드로 갖고 있기 때문이다. 체인을 만든 뒤 크기와 타입 이름을 출력했다.

use std::mem::size_of_val;

fn main() {
    let numbers = vec![1, 2, 3, 4];
    let threshold = 15;

    let iter = numbers.iter();
    println!("iter          = {} bytes", size_of_val(&iter));

    let mapped = numbers.iter().map(|n| n * 10);
    println!("map           = {} bytes", size_of_val(&mapped));

    let filtered = numbers.iter().map(|n| n * 10).filter(|n| *n > threshold);
    println!("map + filter  = {} bytes", size_of_val(&filtered));
    println!("{}", std::any::type_name_of_val(&filtered));

    let total: i32 = filtered.sum();
    println!("sum = {total}");
}

iter          = 16 bytes
map           = 16 bytes
map + filter  = 24 bytes
core::iter::adapters::filter::Filter<core::iter::adapters::map::Map<core::slice::iter::Iter<'_, i32>, adapter_size::main::{{closure}}>, adapter_size::main::{{closure}}>
sum = 90

타입 이름이 그림의 중첩 구조 그대로다. Filter<Map<Iter<i32>, 클로저>, 클로저> 다. slice::Iter 는 16바이트이고, 아무것도 캡처하지 않은 map 클로저는 0바이트라 Map 도 16바이트다. filter 클로저는 &threshold 를 캡처해 8바이트를 더한다. 첫 절에서 본 클로저 크기 계산이 어댑터 체인 크기에 그대로 나타난다.

각 클로저는 고유한 타입이라 Filter 와 Map 도 그 클로저 타입마다 monomorphization 으로 사본이 만들어진다. 호출할 클로저가 컴파일할 때 정해지므로 인라인도 가능하다. 이 글에서 생성된 코드나 실행 시간을 측정하지는 않았다.

collect — 결과 타입을 정해 줘야 한다#

collect 는 iterator 를 소비해 컬렉션을 만든다. 무엇을 만들지는 반환 타입으로 정해지므로, 타입을 알려 주지 않으면 컴파일되지 않는다.

fn main() {
    let numbers = vec![1, 2, 3];
    let doubled = numbers.iter().map(|n| n * 2).collect();
    println!("{doubled:?}");
}

collect 의 반환 타입 B 는 FromIterator<Self::Item> 을 구현한 타입이면 된다. 원소 타입은 _ 로 두고 컬렉션 종류만 적어도 된다. 같은 collect 가 Vec, HashMap, String 을 모두 만든다.

use std::collections::HashMap;

fn main() {
    let words = vec!["fig", "apple", "banana"];

    let lengths: Vec<usize> = words.iter().map(|w| w.len()).collect();
    let by_len: HashMap<usize, &str> = words.iter().map(|w| (w.len(), *w)).collect();
    let initials: String = words.iter().map(|w| w.chars().next().unwrap()).collect();

    println!("{lengths:?}");
    println!("{:?}", by_len.get(&5));
    println!("{initials}");
}

Some("apple")

(키, 값) 튜플을 내는 iterator 는 HashMap 으로, char 를 내는 iterator 는 String 으로 모인다. 어느 쪽이든 체인의 원소를 실제로 꺼내는 것은 이 collect 호출이다.

마무리#

클로저는 캡처한 값을 필드로 가진 struct 였다. 본문이 읽기만 하는 read 는 8바이트 참조를, String 을 소비하는 consume 은 24바이트 String 을 담았다. move 는 이 캡처 방식만 값으로 바꾸고, 본문이 읽기만 하면 그 클로저는 여전히 Fn 이었다. Fn·FnMut·FnOnce 는 본문이 캡처한 값을 읽는지, 바꾸는지, 소비하는지로 정해진다.

iterator 쪽도 같은 구조였다. map·filter 는 앞 iterator 와 클로저를 필드로 가진 struct 를 하나 더 쌓을 뿐이고, collect 가 next 를 부를 때 원소 하나씩 체인을 지났다. take(1) 이 채워지자 3 과 4 는 꺼내지도 않았다. 클로저가 무엇을 담는지와 어댑터가 언제 그 클로저를 부르는지를 알면, 체인 한 줄이 무슨 일을 하는지 읽힌다고 봤다.
