Rust 메모리 배치와 할당

Rust 에서 크기가 정해진(Sized) 타입의 값 하나가 차지하는 바이트 수는 컴파일 시점에 정해지고, std::mem::size_of 로 바로 볼 수 있다. 힙 할당이 언제 일어나는지도 Vec::capacity 같은 값으로 코드에서 드러난다. 요청마다 작은 구조체와 Vec 을 많이 만드는 API 서버에서는 값의 크기와 할당 횟수가 메모리 사용량과 처리 시간에 영향을 줄 수 있다. 그래서 어떤 타입이 몇 바이트인지, 어떤 코드가 몇 번 할당하는지를 직접 재 보고 싶었다.

크기와 배치는 size_of·align_of·offset_of! 출력으로, 할당 비용은 criterion 벤치마크로 확인했다. 아래 예제는 모두 rustc 1.94.1, edition 2021 에서 컴파일하고 aarch64-apple-darwin(Apple M4 Pro, macOS 15.1)에서 실행했다. 크기는 64비트 타깃 기준이고, Rust Reference 가 보장하지 않는 배치는 이 버전에서 측정한 값이다. 벤치마크에 쓴 crate 는 smallvec 1.16.5, bumpalo 3.20.4, criterion 0.5.1 이다.

크기와 정렬 — 필드 순서가 패딩을 정한다#

타입마다 크기(size)와 정렬(alignment)이 있다. 정렬이 4 인 값은 주소가 4의 배수인 곳에만 놓인다. 같은 필드 셋을 기본 배치와 #[repr(C)] 로 선언하고 오프셋을 찍었다.

use std::mem::{align_of, offset_of, size_of};

struct Event {
    kind: u8,
    id: u32,
    flags: u16,
}

#[repr(C)]
struct EventC {
    kind: u8,
    id: u32,
    flags: u16,
}

fn main() {
    println!("u8  size {} align {}", size_of::<u8>(), align_of::<u8>());
    println!("u16 size {} align {}", size_of::<u16>(), align_of::<u16>());
    println!("u32 size {} align {}", size_of::<u32>(), align_of::<u32>());
    println!("u64 size {} align {}", size_of::<u64>(), align_of::<u64>());

    println!(
        "Event  size {} align {} | kind @{} id @{} flags @{}",
        size_of::<Event>(),
        align_of::<Event>(),
        offset_of!(Event, kind),
        offset_of!(Event, id),
        offset_of!(Event, flags)
    );
    println!(
        "EventC size {} align {} | kind @{} id @{} flags @{}",
        size_of::<EventC>(),
        align_of::<EventC>(),
        offset_of!(EventC, kind),
        offset_of!(EventC, id),
        offset_of!(EventC, flags)
    );
    println!("[Event; 4]  = {} bytes", size_of::<[Event; 4]>());
    println!("[EventC; 4] = {} bytes", size_of::<[EventC; 4]>());
}

u8  size 1 align 1
u16 size 2 align 2
u32 size 4 align 4
u64 size 8 align 8
Event  size 8 align 4 | kind @6 id @0 flags @4
EventC size 12 align 4 | kind @0 id @4 flags @8
[Event; 4]  = 32 bytes
[EventC; 4] = 48 bytes

필드 크기를 더하면 7바이트다. #[repr(C)] 는 C 와 같은 규칙으로 선언 순서를 지킨다. kind 다음의 id 가 4의 배수 주소에 놓이도록 3바이트를 비우고, 끝에서 다시 2바이트를 채워 12바이트가 됐다. The Rust Reference 는 크기가 항상 정렬의 배수라고 정의한다. 배열에서 다음 원소도 정렬된 주소에서 시작해야 하기 때문이다.

기본 배치(repr(Rust))는 id, flags, kind 순으로 필드를 바꿔 놓아 패딩이 1바이트로 줄었다. Reference 는 기본 배치에 대해 각 필드가 정렬되고 겹치지 않는 정도만 보장하고, 필드 순서는 컴파일러가 정한다. 위 오프셋은 rustc 1.94.1 이 고른 결과일 뿐이다. 원소 4개 배열에서 차이는 16바이트로 커졌다. 다른 언어와 메모리를 주고받거나 바이트 배치에 의존해야 할 때만 #[repr(C)] 를 쓰고, 그 외에는 컴파일러에 맡기면 된다.

enum — tag 로 variant 를 구분한다#

데이터를 가진 enum 은 지금 어느 variant 인지 나타내는 구분값(tag)과, 가장 큰 variant 를 담을 자리를 함께 갖는다. 그런데 tag 가 필요 없는 enum 도 있다.

use std::mem::size_of;
use std::num::NonZeroU32;

#[allow(dead_code)]
enum Shape {
    Point,
    Circle(f64),
    Rect(f64, f64),
}

#[allow(dead_code)]
enum List {
    Cons(i32, Box<List>),
    Nil,
}

fn main() {
    println!("Shape               = {}", size_of::<Shape>());
    println!("u32                 = {}", size_of::<u32>());
    println!("Option<u32>         = {}", size_of::<Option<u32>>());
    println!("NonZeroU32          = {}", size_of::<NonZeroU32>());
    println!("Option<NonZeroU32>  = {}", size_of::<Option<NonZeroU32>>());
    println!("&u64                = {}", size_of::<&u64>());
    println!("Option<&u64>        = {}", size_of::<Option<&u64>>());
    println!("Option<Box<u64>>    = {}", size_of::<Option<Box<u64>>>());
    println!("Option<bool>        = {}", size_of::<Option<bool>>());
    println!("String              = {}", size_of::<String>());
    println!("Option<String>      = {}", size_of::<Option<String>>());
    println!("List                = {}", size_of::<List>());
}

Shape               = 24
u32                 = 4
Option<u32>         = 8
NonZeroU32          = 4
Option<NonZeroU32>  = 4
&u64                = 8
Option<&u64>        = 8
Option<Box<u64>>    = 8
Option<bool>        = 1
String              = 24
Option<String>      = 24
List                = 16

Shape 는 Rect 의 f64 두 개 16바이트에 tag 가 더해져 24바이트다. tag 와 패딩에 8바이트가 들어간 것은 다음 f64 가 8의 배수 주소에 놓여야 해서다. Option<u32> 도 같은 이유로 u32 4바이트에 tag 와 패딩 4바이트가 붙어 8바이트가 됐다.

Option<NonZeroU32>, Option<&u64>, Option<Box<u64>> 는 감싼 타입과 크기가 같다. NonZeroU32 는 0 이 될 수 없고, 참조와 Box 는 null 이 될 수 없다. 타입이 절대 갖지 않는 이 값(niche)을 컴파일러가 None 표시로 쓴다. std 의 Option 문서는 &U, &mut U, Box<U>, NonZero* 등에 대해 Option<T> 가 T 와 크기·정렬이 같다고 보장하고, 이를 null pointer optimization 이라 부른다.

Option<bool> 이 1바이트인 것도 같은 원리로 보인다. bool 은 0 과 1 만 쓰므로, 그 밖의 값 하나를 None 에 쓸 수 있다. Option<bool> 과 Option<String> 이 감싼 타입과 같은 크기인 것은 std 문서의 보장 목록에 없고, 이 버전에서 측정한 결과다.

스마트 포인터 글의 List 는 16바이트였다. Cons 는 i32 4바이트, 패딩 4바이트, Box 8바이트다. 그런데 이 크기만으로는 Nil 을 Box 의 0 으로 표현했는지, 패딩 자리에 tag 를 두었는지 구분할 수 없다. Box 를 usize 로 바꾼 enum 과 비교했다.

use std::mem::size_of;

#[allow(dead_code)]
enum List {
    Cons(i32, Box<List>),
    Nil,
}

#[allow(dead_code)]
enum RawList {
    Cons(i32, usize),
    Nil,
}

#[allow(dead_code)]
enum Link {
    More(Box<u64>),
    Empty,
}

#[allow(dead_code)]
enum RawLink {
    More(usize),
    Empty,
}

fn main() {
    println!("List    = {}", size_of::<List>());
    println!("RawList = {}", size_of::<RawList>());
    println!("Link    = {}", size_of::<Link>());
    println!("RawLink = {}", size_of::<RawLink>());
}

List    = 16
RawList = 16
Link    = 8
RawLink = 16

List 와 RawList 는 둘 다 16바이트라 차이가 드러나지 않는다. i32 뒤 패딩 4바이트에 tag 를 넣을 수 있기 때문이다. 패딩이 없는 Link 와 RawLink 에서는 갈렸다. usize 는 0 도 쓰는 값이라 RawLink 에는 tag 가 붙어 16바이트가 됐고, Box 를 가진 Link 는 tag 없이 8바이트다. Empty 를 Box 가 갖지 않는 값 0 으로 표현한 것이다.

참조와 컨테이너의 크기#

참조와 표준 컨테이너의 크기는 8바이트에서 24바이트로 갈린다. 길이나 용량, 상태를 함께 가지면 커진다.

use std::cell::RefCell;
use std::mem::size_of;
use std::rc::Rc;
use std::sync::{Arc, Mutex};

fn main() {
    println!("&u64         = {}", size_of::<&u64>());
    println!("&[u64]       = {}", size_of::<&[u64]>());
    println!("&str         = {}", size_of::<&str>());
    println!("Box<u64>     = {}", size_of::<Box<u64>>());
    println!("Box<[u64]>   = {}", size_of::<Box<[u64]>>());
    println!("Vec<u64>     = {}", size_of::<Vec<u64>>());
    println!("String       = {}", size_of::<String>());
    println!("Rc<u64>      = {}", size_of::<Rc<u64>>());
    println!("Arc<u64>     = {}", size_of::<Arc<u64>>());
    println!("RefCell<u64> = {}", size_of::<RefCell<u64>>());
    println!("Mutex<u64>   = {}", size_of::<Mutex<u64>>());
}

&u64         = 8
&[u64]       = 16
&str         = 16
Box<u64>     = 8
Box<[u64]>   = 16
Vec<u64>     = 24
String       = 24
Rc<u64>      = 8
Arc<u64>     = 8
RefCell<u64> = 16
Mutex<u64>   = 24

&[u64] 와 &str 은 길이를 함께 가진 fat pointer 라 16바이트다. Box<[u64]> 도 같다. Vec 과 String 은 여기에 용량이 더해져 24바이트다. Rc 와 Arc 는 카운트를 값과 함께 힙에 두므로 스택에는 포인터 8바이트만 남는다. RefCell<u64> 는 대여 상태를 기록할 칸 8바이트가 값 옆에 붙었다. Mutex<u64> 의 24바이트는 이 플랫폼의 잠금 구현에 따른 값이라, 다른 타깃에서는 다를 수 있다.

Vec 과 String — 스택에 24바이트, 원소는 힙에#

std 문서는 Vec 이 힙 할당을 가리키는 포인터, 길이, 용량으로 이뤄진다고 적는다(필드 순서는 보장하지 않는다). 길이(len)는 지금 든 원소 수, 용량(cap)은 다시 할당하지 않고 담을 수 있는 원소 수다. String 도 포인터·길이·용량이고, 그 버퍼에 UTF-8 바이트가 들어 있다. len == cap 인 상태에서 push 하면 더 큰 버퍼를 새로 할당한다. 그 순간을 용량 변화로 출력했다.

fn main() {
    let mut ids: Vec<u64> = Vec::new();
    println!("new:  len {:<3} cap {}", ids.len(), ids.capacity());
    let mut grows = 0;
    for id in 0..100u64 {
        let before = ids.capacity();
        ids.push(id);
        if ids.capacity() != before {
            grows += 1;
            println!("push: len {:<3} cap {}", ids.len(), ids.capacity());
        }
    }
    println!("capacity changes while pushing 100: {grows}");

    let mut sized: Vec<u64> = Vec::with_capacity(100);
    let start_cap = sized.capacity();
    for id in 0..100u64 {
        sized.push(id);
    }
    println!("with_capacity(100): cap {} -> {}", start_cap, sized.capacity());

    let mut name = String::from("rust");
    println!("String: len {} cap {}", name.len(), name.capacity());
    name.push_str(" memory");
    println!("String: len {} cap {}", name.len(), name.capacity());
}

new:  len 0   cap 0
push: len 1   cap 4
push: len 5   cap 8
push: len 9   cap 16
push: len 17  cap 32
push: len 33  cap 64
push: len 65  cap 128
capacity changes while pushing 100: 6
with_capacity(100): cap 100 -> 100
String: len 4 cap 4
String: len 11 cap 11

Vec::new() 는 용량 0 으로 시작해 할당하지 않는다. 첫 push 에서 4칸을 할당했고, 그 뒤로는 가득 찰 때마다 두 배로 늘었다. 100개를 넣는 동안 첫 할당을 포함해 6번 할당했고, 같은 코드를 1000개로 따로 실행하면 9번이었다. with_capacity(100) 은 처음 한 번 100칸을 확보해 용량이 바뀌지 않았다. 다만 std 문서는 Vec 이 특정한 증가 방식을 보장하지 않는다고 적는다. 4칸 시작과 두 배 증가는 이 버전의 동작이다. String 은 4바이트에서 11바이트가 필요해지자 두 배인 8 대신 필요한 11 을 할당했다.

SmallVec — 작으면 힙에 가지 않는다#

원소가 서너 개뿐인 Vec 도 첫 push 에서 힙 할당이 한 번 일어난다. smallvec crate 의 SmallVec<[T; N]> 은 원소 N 개까지 자기 안에 두고, 넘치면 힙으로 옮긴다. 이것을 spill 이라고 부른다.

use smallvec::SmallVec;
use std::mem::size_of;

fn main() {
    println!("Vec<u32>           = {} bytes", size_of::<Vec<u32>>());
    println!("SmallVec<[u32; 4]> = {} bytes", size_of::<SmallVec<[u32; 4]>>());

    let mut tags: SmallVec<[u32; 4]> = SmallVec::new();
    for tag in 1..=5 {
        tags.push(tag);
        println!("push {tag}: len {} cap {} spilled {}", tags.len(), tags.capacity(), tags.spilled());
    }
}

Vec<u32>           = 24 bytes
SmallVec<[u32; 4]> = 32 bytes
push 1: len 1 cap 4 spilled false
push 2: len 2 cap 4 spilled false
push 3: len 3 cap 4 spilled false
push 4: len 4 cap 4 spilled false
push 5: len 5 cap 8 spilled true

spilled() 는 원소가 별도의 힙 버퍼로 옮겨졌는지를 돌려준다. 4개까지는 false 였고, 5번째 push 에서 용량 8 인 힙 버퍼로 옮겨 true 가 됐다. 대신 SmallVec 자체는 Vec 보다 8바이트 크다. 인라인 칸을 쓰지 않을 때도 그 자리를 차지한다. 원소 수가 대개 N 이하로 정해지는 곳에 맞고, 자주 넘치면 크기만 커지고 할당은 그대로 일어난다.

arena — 모아서 할당하고 한 번에 비운다#

트리나 그래프 노드를 Box::new 로 하나씩 만들면 노드마다 할당과 해제가 한 번씩 일어난다. arena 는 큰 메모리 덩어리(chunk)를 미리 할당해 두고 그 안에 값을 차례로 놓는다. bumpalo crate 의 Bump 는 청크 안에 위치 하나를 두고, 할당 요청이 오면 남은 공간을 확인한 뒤 그 위치를 값 크기만큼 옮긴다(bump). 개별 해제는 없고, reset() 이 위치를 청크 처음으로 되돌려 한 번에 비운다. 청크가 여러 개로 늘었으면 하나만 남기고 나머지는 전역 할당자에 돌려준다.

use bumpalo::Bump;
use std::mem::size_of;

struct Node {
    id: u64,
    weight: u64,
}

impl Drop for Node {
    fn drop(&mut self) {
        println!("drop node {}", self.id);
    }
}

fn main() {
    let mut arena = Bump::new();
    let first = arena.alloc(Node { id: 1, weight: 10 });
    let second = arena.alloc(Node { id: 2, weight: 20 });
    let gap = (second as *const Node as usize).abs_diff(first as *const Node as usize);
    println!("weight sum = {}", first.weight + second.weight);
    println!("gap = {gap} bytes, size_of::<Node>() = {}", size_of::<Node>());

    arena.reset();
    println!("after reset");

    let boxed = Box::new(Node { id: 3, weight: 30 });
    drop(boxed);
    println!("end of main");
}

weight sum = 30
gap = 16 bytes, size_of::<Node>() = 16
after reset
drop node 3
end of main

두 노드의 주소 차이가 Node 크기와 같은 16바이트다. 빈틈없이 붙어 있다. alloc 은 &self 로 arena 를 공유 대여하고, 그 대여에 묶인 &mut Node 를 돌려준다. reset() 은 &mut self 를 받으므로, arena 에서 받은 참조를 reset() 뒤에 쓰면 컴파일되지 않는다.

use bumpalo::Bump;

fn main() {
    let mut arena = Bump::new();
    let first = arena.alloc(1u64);
    arena.reset();
    println!("{first}");
}

error[E0502]: cannot borrow `arena` as mutable because it is also borrowed as immutable
 --> examples/arena_err.rs:6:5
  |
5 |     let first = arena.alloc(1u64);
  |                 ----- immutable borrow occurs here
6 |     arena.reset();
  |     ^^^^^^^^^^^^^ mutable borrow occurs here
7 |     println!("{first}");
  |                ----- immutable borrow later used here

참조와 borrow 글의 E0502 다. 돌려준 메모리를 읽는 코드는 대여 규칙으로 컴파일러가 거부한다.

출력에 drop node 1·drop node 2 는 없다. bumpalo 문서는 arena 에 넣은 값의 Drop 이 실행되지 않는다고 적는다. Box 로 만든 노드 3 만 drop 됐다. 파일 핸들이나 Vec 처럼 정리가 필요한 값을 arena 에 넣으면 그 정리가 일어나지 않는다. 정수와 참조처럼 해제할 것이 없는 값을 담는 쪽이 arena 와 맞는다.

criterion 으로 할당 비용 측정#

여기까지는 할당 횟수를 코드로 셌다. 그 횟수가 시간으로 얼마인지는 criterion 으로 쟀다. 블로그 저장소 밖의 별도 cargo 프로젝트에 아래 의존성을 두고, benches/alloc.rs 로 세 쌍을 비교했다.

[dependencies]
bumpalo = "3"
smallvec = "1"

[dev-dependencies]
criterion = "0.5"

[[bench]]
name = "alloc"
harness = false

use bumpalo::Bump;
use criterion::{black_box, criterion_group, criterion_main, Criterion};
use smallvec::SmallVec;

const IDS: u64 = 1000;
const GROUPS: u32 = 1000;
const NODES: u64 = 1000;

struct Node {
    id: u64,
    weight: u64,
}

fn vec_growth(c: &mut Criterion) {
    let mut group = c.benchmark_group("push 1000 u64");
    group.bench_function("Vec::new", |b| {
        b.iter(|| {
            let mut ids = Vec::new();
            for id in 0..IDS {
                ids.push(black_box(id));
            }
            ids
        })
    });
    group.bench_function("Vec::with_capacity", |b| {
        b.iter(|| {
            let mut ids = Vec::with_capacity(IDS as usize);
            for id in 0..IDS {
                ids.push(black_box(id));
            }
            ids
        })
    });
    group.finish();
}

fn small_groups(c: &mut Criterion) {
    let mut group = c.benchmark_group("1000 groups of 3 u32");
    group.bench_function("Vec", |b| {
        b.iter(|| {
            let mut total = 0;
            for g in 0..GROUPS {
                let mut tags: Vec<u32> = Vec::new();
                for t in 0..3 {
                    tags.push(black_box(g + t));
                }
                total += black_box(tags).len();
            }
            total
        })
    });
    group.bench_function("SmallVec<[u32; 4]>", |b| {
        b.iter(|| {
            let mut total = 0;
            for g in 0..GROUPS {
                let mut tags: SmallVec<[u32; 4]> = SmallVec::new();
                for t in 0..3 {
                    tags.push(black_box(g + t));
                }
                total += black_box(tags).len();
            }
            total
        })
    });
    group.finish();
}

fn nodes(c: &mut Criterion) {
    let mut group = c.benchmark_group("1000 nodes");
    group.bench_function("Box::new each", |b| {
        b.iter(|| {
            let mut all: Vec<Box<Node>> = Vec::with_capacity(NODES as usize);
            for id in 0..NODES {
                all.push(Box::new(Node { id: black_box(id), weight: id * 2 }));
            }
            all.iter().map(|n| n.id + n.weight).sum::<u64>()
        })
    });
    let mut arena = Bump::new();
    group.bench_function("Bump::alloc + reset", |b| {
        b.iter(|| {
            let mut all: Vec<&Node> = Vec::with_capacity(NODES as usize);
            for id in 0..NODES {
                all.push(arena.alloc(Node { id: black_box(id), weight: id * 2 }));
            }
            let sum = all.iter().map(|n| n.id + n.weight).sum::<u64>();
            drop(all);
            arena.reset();
            sum
        })
    });
    group.finish();
}

criterion_group!(benches, vec_growth, small_groups, nodes);
criterion_main!(benches);

black_box 는 컴파일러가 값을 미리 계산하거나 쓰이지 않는 할당을 지우지 못하게 막는다. 처음 버전은 묶음을 collect() 로 만들고 길이만 읽었는데, 원소 3개짜리 Vec 1000개가 4 µs 대로 나와 SmallVec 보다 빨랐다. 묶음 하나에 4 ns 남짓이라 할당이 일어났다고 보기 어려웠다. 길이만 쓰고 버려지는 Vec 의 할당을 최적화가 없앤 것으로 보고, push 와 black_box(tags) 로 바꿔 다시 쟀다. arena 쪽은 Bump 를 한 번 만들어 두고 매 반복 끝에 reset() 하므로, 청크를 처음 할당하는 비용은 측정에 거의 들어가지 않는다.

cargo bench --bench alloc -- --measurement-time 10 으로 세 번 실행했다. 벤치마크마다 3초 warm-up 뒤 10초 동안 100개 샘플을 모은다(실행 로그 기준). 측정하는 동안 같은 머신에서 다른 작업이 실행 중이어서 load average 가 50 에서 87 사이였다. 아래 숫자는 이 머신, 이 부하에서 나온 값이고, 다른 머신에서 같은 값이 나온다는 뜻이 아니다.

비교1회2회3회
Vec::new13.94 µs5.13 µs3.84 µs
Vec::with_capacity7.15 µs3.77 µs5.11 µs
3개 묶음 × 1000, Vec141.94 µs61.73 µs58.12 µs

값은 criterion 이 출력한 time: [하한 추정값 상한] 의 가운데, 반복 한 번당 추정 시간이다. criterion 문서는 양쪽 값이 신뢰구간의 하한과 상한이라고 설명한다.

부하 때문에 같은 벤치마크도 실행마다 몇 배씩 흔들렸다. 그래서 절대값보다 같은 실행 안의 비교를 봤다. SmallVec 은 세 번 모두 Vec 보다 약 7배에서 15배, Bump 는 Box::new 보다 약 7배에서 10배 빨랐다. 두 쌍 모두 한쪽은 원소 묶음이나 노드마다 할당·해제를 하고, 다른 쪽은 그것을 하지 않는다. 반면 with_capacity 는 1·2회에는 빨랐지만 3회에는 오히려 느렸고, 그림의 3회 결과에서 두 신뢰구간이 겹친다. 1000개를 넣는 동안 할당이 9번에서 1번으로 줄 뿐이라, 원소 1000개를 쓰는 시간에 비해 차이가 작기 때문일 수 있다. 이 측정으로는 그 차이를 부하에서 오는 잡음과 구분하지 못했다.

마무리#

Event 는 필드 순서에 따라 12바이트와 8바이트로 갈렸고, Option<u32> 에는 tag 가 붙었지만 Option<&u64> 는 포인터 크기 그대로였다. 크기는 필드 크기와 정렬, 그리고 타입이 쓰지 않는 값이 있는지로 정해진다. 할당 횟수도 capacity() 와 spilled() 로 코드에서 셀 수 있었다. 측정에서 효과가 분명했던 것은 원소 묶음마다, 노드마다 일어나던 할당을 SmallVec 과 Bump 가 없앤 경우였고, 할당 9번을 1번으로 줄인 with_capacity 는 같은 부하에서 차이를 확인하지 못했다. 할당을 줄이는 코드는 그 코드가 없애는 할당 횟수를 먼저 세어 보고 넣는다. 다음 글에서는 unsafe 로 이 배치를 직접 다룰 때 컴파일러 대신 무엇을 책임져야 하는지 본다.
