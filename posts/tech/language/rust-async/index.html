Rust async 와 tokio 스케줄러

2026년 11월 17일 · 약 17분 읽기
목차
  • async fn 은 호출해도 실행되지 않는다
  • poll 과 Waker
  • async fn 을 손으로 풀어 쓴 상태 머신
  • await 이후에도 살아 있는 변수가 Future 의 크기를 정한다
  • Pin — 첫 poll 뒤에는 옮기지 않는다
  • tokio 멀티 스레드 런타임의 work-stealing
  • blocking 호출이 다른 태스크를 늦춘다
  • spawn_blocking 으로 옮기기
  • 마무리
  • 참고

async fn 을 호출해도 본문은 한 줄도 실행되지 않는다. 호출은 Future 를 구현한 값을 하나 만들 뿐이고, 누군가 그 값의 poll 을 호출해야 본문이 다음 .await 까지 진행한다. 진행할 수 없으면 poll 은 나중에 깨워 달라는 Waker 를 맡기고 Pending 으로 바로 돌아온다. tokio 같은 실행기는 이 구조 덕분에 적은 수의 스레드로 많은 태스크를 번갈아 poll 한다. 반대로 poll 안에서 스레드를 오래 점유하면 같은 스레드를 기다리는 다른 태스크가 모두 늦는다. worker 2개인 런타임에서 100ms 짜리 std::thread::sleep 작업 4개를 태스크 안에서 실행하자, 10ms 마다 깨어나야 하는 태스크가 약 200ms 늦었다.

API 서버의 async 핸들러 안에서 동기 DB 드라이버나 파일 I/O 를 호출하면 무엇이 늦어지는지 알고 싶었고, 그래서 Future 가 상태 머신으로 바뀌는 지점부터 tokio 스케줄러까지 차례로 확인했다.

아래 예제는 모두 rustc 1.94.1, edition 2021 로 직접 컴파일하고 aarch64-apple-darwin(Apple M4 Pro 12코어, macOS 15.1)에서 실행했다. tokio 예제는 tokio 1.54.1 을 의존성으로 둔 cargo 프로젝트에서 --release 로 빌드했다. tokio 실험을 실행하는 동안 이 머신은 다른 작업으로 load average 가 82–91 이었다. 시간 측정값은 이 부하 조건의 값이다.

async fn 은 호출해도 실행되지 않는다#

async fn fetch_user(id: u64) -> String {
    println!("fetch_user({id}) running");
    format!("user-{id}")
}

fn main() {
    fetch_user(7);
    println!("called fetch_user");
}

fetch_user(7) 를 호출했지만 fetch_user(7) running 은 출력되지 않았다. 컴파일러 경고의 note 그대로, future 는 .await 하거나 poll 하기 전에는 아무 일도 하지 않는다. std::future::Future 문서도 future 는 그 자체로는 아무 일도 하지 않고(inert), 계산을 진행하려면 누군가 능동적으로 poll 해야 한다고 적는다.

poll 과 Waker#

Future trait 의 메서드는 poll 하나다. 완료됐으면 Poll::Ready(값), 아직이면 Poll::Pending 을 돌려준다. Future::poll 문서는 준비되지 않은 future 가 Pending 을 돌려줄 때 현재 Context 의 Waker 를 복제해 보관하고, 진행할 수 있게 되면 그 Waker 를 깨운다고 설명한다. 깨어난 태스크는 future 를 다시 poll 한다.

이 흐름을 표준 라이브러리만으로 만들었다. block_on 은 future 를 poll 하고, Pending 이면 스레드를 park 해 잠든다. Waker 는 wake 가 불리면 그 스레드를 unpark 한다. Delay 는 처음 poll 될 때 타이머 스레드를 띄우고, 시간이 지나면 보관해 둔 Waker 를 깨운다.

use std::future::Future;
use std::pin::{pin, Pin};
use std::sync::{Arc, Mutex};
use std::task::{Context, Poll, Wake, Waker};
use std::thread::{self, Thread};
use std::time::Duration;

struct ThreadWaker(Thread);

impl Wake for ThreadWaker {
    fn wake(self: Arc<Self>) {
        println!("    [waker] wake -> unpark executor");
        self.0.unpark();
    }
}

fn block_on<F: Future>(fut: F) -> F::Output {
    let mut fut = pin!(fut);
    let waker = Waker::from(Arc::new(ThreadWaker(thread::current())));
    let mut cx = Context::from_waker(&waker);
    for count in 1.. {
        println!("[executor] poll #{count}");
        if let Poll::Ready(output) = fut.as_mut().poll(&mut cx) {
            return output;
        }
        println!("[executor] Pending -> park");
        thread::park();
    }
    unreachable!()
}

struct Delay {
    ms: u64,
    state: Arc<Mutex<DelayState>>,
}

struct DelayState {
    started: bool,
    done: bool,
    waker: Option<Waker>,
}

fn delay(ms: u64) -> Delay {
    let state = DelayState { started: false, done: false, waker: None };
    Delay { ms, state: Arc::new(Mutex::new(state)) }
}

impl Future for Delay {
    type Output = ();

    fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<()> {
        let mut state = self.state.lock().unwrap();
        if state.done {
            return Poll::Ready(());
        }
        state.waker = Some(cx.waker().clone());
        if !state.started {
            state.started = true;
            let (ms, shared) = (self.ms, Arc::clone(&self.state));
            thread::spawn(move || {
                thread::sleep(Duration::from_millis(ms));
                let mut state = shared.lock().unwrap();
                state.done = true;
                state.waker.take().unwrap().wake();
            });
        }
        Poll::Pending
    }
}

async fn handler() -> &'static str {
    println!("  [handler] start");
    delay(50).await;
    println!("  [handler] after first delay");
    delay(30).await;
    println!("  [handler] after second delay");
    "done"
}

fn main() {
    let output = block_on(handler());
    println!("output = {output}");
}

  [handler] start
[executor] Pending -> park
    [waker] wake -> unpark executor
[executor] poll #2
  [handler] after first delay
[executor] Pending -> park
    [waker] wake -> unpark executor
[executor] poll #3
  [handler] after second delay
output = done

handler 는 poll 세 번에 끝났다. 첫 poll 은 start 를 출력하고 첫 delay(50).await 에서 Pending 으로 돌아왔다. 두 번째 poll 은 처음부터가 아니라 첫 .await 다음 줄에서 이어졌다. 실행기는 그 사이 50ms 와 30ms 동안 잠들어 있었고, CPU 를 쓰며 반복해서 poll 하지 않았다. 언제 다시 poll 할지는 Waker 가 알려 줬다.

async fn 을 손으로 풀어 쓴 상태 머신#

두 번째 poll 이 중간에서 이어진 것은, handler 가 반환한 값이 어디까지 진행했는지를 기억하기 때문이다. 컴파일러는 async fn 본문을 .await 지점마다 상태가 하나씩 있는 상태 머신으로 바꾼다. 같은 동작을 enum 으로 직접 썼다. block_on, Delay, delay 는 앞 예제 그대로이고 handler 와 main 만 바꿨다.

enum Handler {
    Start,
    WaitFirst(Delay),
    WaitSecond(Delay),
    Done,
}

impl Future for Handler {
    type Output = &'static str;

    fn poll(mut self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<&'static str> {
        loop {
            match &mut *self {
                Handler::Start => {
                    println!("  [handler] start");
                    *self = Handler::WaitFirst(delay(50));
                }
                Handler::WaitFirst(first) => {
                    if Pin::new(first).poll(cx).is_pending() {
                        return Poll::Pending;
                    }
                    println!("  [handler] after first delay");
                    *self = Handler::WaitSecond(delay(30));
                }
                Handler::WaitSecond(second) => {
                    if Pin::new(second).poll(cx).is_pending() {
                        return Poll::Pending;
                    }
                    println!("  [handler] after second delay");
                    *self = Handler::Done;
                    return Poll::Ready("done");
                }
                Handler::Done => panic!("polled after completion"),
            }
        }
    }
}

fn main() {
    let output = block_on(Handler::Start);
    println!("output = {output}");
}

  [handler] start
[executor] Pending -> park
    [waker] wake -> unpark executor
[executor] poll #2
  [handler] after first delay
[executor] Pending -> park
    [waker] wake -> unpark executor
[executor] poll #3
  [handler] after second delay
output = done

출력이 async fn 버전과 한 줄도 다르지 않다. enum 의 variant 가 .await 지점이고, variant 에 담긴 Delay 가 그 지점에서 기다리는 future 다. 안쪽 future 가 Pending 이면 바깥 future 도 Pending 을 그대로 돌려준다. 실제로 컴파일러가 만드는 타입은 이름이 없고 세부 구현도 이 enum 과 다르다. 여기서는 상태를 enum 으로 기억하고 poll 마다 이어서 진행한다는 구조만 같게 만들었다.

await 이후에도 살아 있는 변수가 Future 의 크기를 정한다#

상태 머신의 각 상태는 .await 이후에 다시 쓸 값을 저장해야 한다. 그러면 future 의 크기는 .await 이후에도 살아 있는 지역 변수로 정해질 것이다. 1KB 배열을 두는 위치만 바꿔 size_of_val 로 재 봤다. YieldOnce 는 처음 poll 될 때 한 번 Pending 을 돌려주는 future 다.

use std::future::Future;
use std::pin::Pin;
use std::task::{Context, Poll};

struct YieldOnce {
    yielded: bool,
}

impl Future for YieldOnce {
    type Output = ();
    fn poll(mut self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<()> {
        if self.yielded {
            return Poll::Ready(());
        }
        self.yielded = true;
        cx.waker().wake_by_ref();
        Poll::Pending
    }
}

fn yield_once() -> YieldOnce {
    YieldOnce { yielded: false }
}

async fn no_buffer() -> usize {
    yield_once().await;
    1
}

async fn buffer_before_await() -> usize {
    let buf = [0u8; 1024];
    let n = buf.len();
    yield_once().await;
    n
}

async fn buffer_across_await() -> usize {
    let buf = [0u8; 1024];
    yield_once().await;
    buf.len()
}

async fn buffer_in_block() -> usize {
    let n = {
        let buf = [0u8; 1024];
        buf.len()
    };
    yield_once().await;
    n
}

fn main() {
    println!("no_buffer           = {} bytes", size_of_val(&no_buffer()));
    println!("buffer_before_await = {} bytes", size_of_val(&buffer_before_await()));
    println!("buffer_in_block     = {} bytes", size_of_val(&buffer_in_block()));
    println!("buffer_across_await = {} bytes", size_of_val(&buffer_across_await()));
}

no_buffer           = 2 bytes
buffer_before_await = 1040 bytes
buffer_in_block     = 16 bytes
buffer_across_await = 1026 bytes

buffer_across_await 는 .await 뒤에서 buf 를 쓰므로 1KB 가 상태에 포함된다. buffer_before_await 는 .await 전에 buf.len() 을 n 에 담아 두고 buf 는 다시 쓰지 않는데도 1040바이트가 됐다. buf 의 스코프가 함수 끝까지라 .await 이후에도 살아 있는 변수로 저장되고, n 도 함께 들어간 것으로 보인다. 블록 { } 으로 스코프를 .await 전에 닫은 buffer_in_block 은 16바이트였다. rustc 1.94.1 에서 크기를 가른 것은 변수의 마지막 사용 위치가 아니라 스코프가 .await 를 지나는지였다. --release(-O) 로 빌드해도 네 값은 같았다.

future 는 보통 tokio::spawn 으로 태스크가 되어 힙에 저장되고, .await 로 기다리는 future 는 바깥 future 안에 그대로 들어간다. 큰 버퍼의 스코프가 .await 를 지나면 태스크 하나의 메모리가 그만큼 늘어난다.

Pin — 첫 poll 뒤에는 옮기지 않는다#

async fn 본문은 자기 지역 변수를 가리키는 참조를 .await 이후까지 쓸 수 있다. 상태 머신으로 바뀌면 그 지역 변수와 참조가 같은 future 값 안의 필드가 된다. 자기 자신의 다른 필드를 가리키는 값이다. std::pin 모듈 문서는 이런 자기 참조 타입을 옮기면 포인터는 여전히 옛 주소를 가리켜 무효가 된다고 설명하고, 대표 예로 컴파일러가 async fn 에 만드는 상태 머신을 든다.

같은 문서는 이런 값이 거치는 단계를 나눠 설명한다. 만들어진 직후에는 자유롭게 옮길 수 있다. async fn 을 호출해 future 를 받은 시점이 여기에 해당한다. 처음 poll 한 뒤부터 값은 자기 주소가 바뀌지 않는다고 가정하고 동작하며, 이후의 poll 도 그 가정에 의존한다. Pin<Ptr> 는 가리키는 값이 drop 될 때까지 옮겨지지 않는다는 약속을 타입으로 표시한다. poll 이 self: Pin<&mut Self> 를 받는 이유다.

// YieldOnce, yield_once 는 앞 예제와 같다 (생략)

async fn checksum() -> usize {
    let buf = [1u8; 16];
    let head = &buf[..4];
    yield_once().await;
    head.iter().map(|b| *b as usize).sum()
}

fn require_unpin<F: Future + Unpin>(_fut: &F) {}

fn main() {
    require_unpin(&yield_once());
    require_unpin(&checksum());
}

줄 번호는 YieldOnce 를 생략하기 전 파일 기준이다. Unpin 은 옮겨도 문제없는 타입에 붙는 auto trait 다. 필드가 모두 Unpin 이면 자동으로 구현되므로, bool 하나뿐인 YieldOnce 는 통과했다. checksum() 의 future 는 Unpin 이 아니라서 거부됐다. 참조가 없는 async { 1 } 블록으로 바꿔도 같은 E0277 이 났다. rustc 1.94.1 에서 async 블록과 async fn 의 future 는 실제로 자기 참조가 있는지와 관계없이 Unpin 이 아니었다.

Pin<Box<_>> 는 힙 주소를 가리키는 포인터일 뿐이라 포인터 자체를 옮겨도 future 의 주소는 바뀌지 않기 때문이다. 손으로 쓴 Handler enum 이 Pin::new 로 간단히 안쪽 Delay 를 poll 할 수 있었던 것도 Delay 의 필드가 u64 와 Arc 라 Unpin 이어서다.

tokio 멀티 스레드 런타임의 work-stealing#

tokio 는 tokio::spawn 으로 받은 future 를 태스크로 만들고, 깨어난 태스크를 poll 한다. 멀티 스레드 런타임은 기본으로 CPU 코어 수만큼 worker 스레드를 띄운다. tokio 1.54.1 의 tokio::runtime 모듈 문서가 “작성 시점의 동작"으로 설명하는 구조는 이렇다. 이후 버전에서 바뀔 수 있다고 명시돼 있다.

  • worker 마다 local queue 가 하나씩 있고, 런타임 전체에 global queue 가 하나 있다
  • local queue 에는 태스크가 최대 256개 들어간다. 넘치면 절반을 global queue 로 옮긴다
  • worker 는 local queue 를 먼저 보고, 비었거나 global_queue_interval 번 연속 local 에서 꺼냈으면 global queue 를 본다. 이 값을 지정하지 않으면 global queue 확인 간격이 약 10ms 가 되도록 런타임이 계산한다
  • local 과 global 이 모두 비면 다른 worker 의 local queue 에서 절반을 훔쳐 온다
  • 태스크가 다른 태스크를 깨우면 깨어난 태스크는 큐 대신 그 worker 의 lifo slot 에 들어가, 지금 태스크가 끝나면 바로 실행된다. lifo slot 의 태스크는 다른 worker 가 훔쳐 가지 못한다
  • worker 스레드가 아닌 곳에서 깨운 태스크는 global queue 로 간다

태스크 하나 안에서 200개를 spawn 하고, 각 태스크를 실행한 스레드 이름을 셌다.

use std::collections::BTreeMap;
use std::sync::atomic::{AtomicUsize, Ordering};
use std::time::Duration;
use tokio::runtime::Builder;

fn main() {
    static NEXT: AtomicUsize = AtomicUsize::new(0);
    let runtime = Builder::new_multi_thread()
        .worker_threads(4)
        .thread_name_fn(|| format!("worker-{}", NEXT.fetch_add(1, Ordering::Relaxed)))
        .build()
        .unwrap();

    let counts = runtime.block_on(async {
        // 태스크 하나 안에서 200개를 spawn 한다 → 이 worker 의 local queue 에 들어간다
        let spawner = tokio::spawn(async {
            let spawner_thread = std::thread::current().name().unwrap().to_string();
            let handles: Vec<_> = (0..200)
                .map(|_| {
                    tokio::spawn(async {
                        std::thread::sleep(Duration::from_millis(1));
                        std::thread::current().name().unwrap().to_string()
                    })
                })
                .collect();
            let mut counts = BTreeMap::new();
            for handle in handles {
                *counts.entry(handle.await.unwrap()).or_insert(0) += 1;
            }
            (spawner_thread, counts)
        });
        spawner.await.unwrap()
    });
    println!("spawned on {}", counts.0);
    for (thread, count) in counts.1 {
        println!("{thread}: {count} tasks");
    }
}

각 태스크 안의 std::thread::sleep(1ms) 는 태스크가 바로 끝나지 않게 해서 다른 worker 가 가져갈 시간을 주려고 일부러 넣었다. 다음 절에서 보듯 실제 코드에서는 피해야 하는 호출이다. 세 번 실행해 spawn 한 worker 는 매번 달랐고, 네 worker 가 47–53개씩 나눠 실행했다. 200개는 local queue 한도 256 보다 적어 global queue 로 넘어가지 않으므로, spawn 한 worker 가 아닌 곳에서 실행된 태스크는 다른 worker 가 훔쳐 간 것으로 봤다. 훔쳐 가는 쪽은 할 일이 없는 worker 다. 모든 worker 가 한 태스크의 poll 안에 묶여 있으면 큐에 쌓인 태스크를 가져갈 worker 가 없다.

blocking 호출이 다른 태스크를 늦춘다#

worker 는 태스크의 poll 이 돌아와야 다음 태스크를 꺼낸다. Future::poll 문서도 poll 구현은 빨리 돌아와야 하고 blocking 하면 안 되며, 오래 걸릴 일은 스레드 풀 같은 곳으로 넘기라고 적는다. tokio 런타임 문서의 공정성 보장도 어떤 태스크도 스레드를 blocking 하지 않는다는 전제를 단다.

worker 2개짜리 런타임에서 10ms 마다 깨어나는 ticker 태스크를 띄워 두고, 100ms 걸리는 작업 4개를 세 가지 방식으로 실행했다. ticker 는 30번 깨어나면서 예정보다 늦게 깨어난 시간을 기록한다.

use std::time::{Duration, Instant};
use tokio::runtime::Builder;

#[derive(Clone, Copy, Debug)]
enum Job {
    AsyncSleep,
    ThreadSleep,
    SpawnBlocking,
}

const TICK: Duration = Duration::from_millis(10);
const JOB_TIME: Duration = Duration::from_millis(100);

// 10ms 마다 깨어나며, 예정보다 늦게 깨어난 시간을 모은다
async fn ticker() -> Vec<Duration> {
    let mut lateness = Vec::new();
    for _ in 0..30 {
        let start = Instant::now();
        tokio::time::sleep(TICK).await;
        lateness.push(start.elapsed().saturating_sub(TICK));
    }
    lateness
}

async fn run_job(job: Job) {
    match job {
        Job::AsyncSleep => tokio::time::sleep(JOB_TIME).await,
        Job::ThreadSleep => std::thread::sleep(JOB_TIME),
        Job::SpawnBlocking => tokio::task::spawn_blocking(|| std::thread::sleep(JOB_TIME))
            .await
            .unwrap(),
    }
}

fn run(job: Job) {
    let runtime = Builder::new_multi_thread()
        .worker_threads(2)
        .enable_all()
        .build()
        .unwrap();
    runtime.block_on(async {
        let ticks = tokio::spawn(ticker());
        tokio::time::sleep(Duration::from_millis(20)).await;

        let started = Instant::now();
        let jobs: Vec<_> = (0..4).map(|_| tokio::spawn(run_job(job))).collect();
        for handle in jobs {
            handle.await.unwrap();
        }
        let jobs_elapsed = started.elapsed();

        let mut lateness = ticks.await.unwrap();
        lateness.sort();
        println!(
            "{:<13} jobs {:>4.0?}  tick lateness p50 {:>6.1?}  max {:>6.1?}",
            format!("{job:?}"),
            jobs_elapsed,
            lateness[lateness.len() / 2],
            lateness[lateness.len() - 1],
        );
    });
}

fn main() {
    for _ in 0..3 {
        for job in [Job::AsyncSleep, Job::ThreadSleep, Job::SpawnBlocking] {
            run(job);
        }
    }
}

  • ThreadSleep 은 std::thread::sleep 이 worker 를 100ms 동안 점유한다. worker 2개가 작업 4개를 두 개씩 차례로 실행해 끝나는 데 204–206ms 가 걸렸다. 최대 지연은 202–206ms 였다
  • AsyncSleep 은 tokio::time::sleep 이 바로 Pending 을 돌려주므로 worker 가 비어 있다. 네 작업이 동시에 기다려 102–103ms 에 끝났고, 최대 지연은 4.5–9.8ms 였다
  • SpawnBlocking 은 같은 std::thread::sleep 을 blocking 스레드 풀에서 실행했다. 네 작업이 따로 스레드를 받아 104–112ms 에 끝났고, 최대 지연은 2.8–6.7ms 였다
  • 지연 중앙값은 세 방식 모두 2ms 안팎이다. tokio::time::sleep 문서가 밝히듯 타이머가 밀리초 단위라 이 정도는 blocking 이 없어도 생긴다

ThreadSleep 의 지연이 100ms 가 아니라 약 200ms 인 것은 tokio 문서의 설명으로 이렇게 읽힌다. worker 는 실행할 태스크가 없을 때, 또는 태스크를 61개 연속 실행했을 때 타이머 이벤트를 확인한다. 100ms 에 첫 작업을 끝낸 worker 에게는 큐에 남은 작업이 있어서, 타이머를 확인하지 않고 바로 다음 작업을 실행했다. 두 worker 가 모두 두 번째 작업까지 끝낸 약 200ms 에야 ticker 의 타이머가 처리됐다. 이 순서는 tokio 내부를 추적해 확인하지 않았고, 측정값과 문서가 맞아떨어진다는 것까지만 확인했다.

부하가 높은 머신이라 AsyncSleep 의 최대 지연도 실행마다 4.5–9.8ms 로 달라졌다. 그래도 ThreadSleep 의 200ms 는 그 변동과 자릿수가 다르다. 동기 DB 드라이버 호출이나 std::fs 파일 읽기, 큰 JSON 파싱 같은 CPU 작업은 실험하지 않았다. 다만 끝날 때까지 poll 이 돌아오지 않아 worker 를 점유한다는 점은 std::thread::sleep 과 같다.

spawn_blocking 으로 옮기기#

tokio::task::spawn_blocking 은 클로저를 blocking 작업 전용 스레드에서 실행하고, 그 결과를 기다리는 JoinHandle 을 돌려준다. async 태스크는 그 JoinHandle 을 .await 하며 Pending 으로 돌아오므로 worker 가 비워진다. 아래는 tokio 문서에 적힌 동작이다.

  • blocking 스레드는 요청이 올 때 늘리고, max_blocking_threads 상한(기본 512)에 닿으면 작업을 큐에 넣는다. 이 큐는 backpressure 가 없어 한없이 길어질 수 있다
  • 상한이 큰 것은 비동기로 할 수 없는 I/O 에 주로 쓰이기 때문이다. CPU 작업을 많이 넘긴다면 semaphore 등으로 동시에 실행할 수를 제한하라고 권한다. rayon 같은 CPU 전용 실행기도 후보로 든다
  • 시작된 spawn_blocking 작업은 abort 해도 멈추지 않는다. 런타임을 종료할 때도 시작된 작업이 끝나기를 기다린다
  • 끝나지 않는 작업이나 오래 사는 작업은 blocking 풀의 스레드를 계속 차지하므로, thread::spawn 으로 전용 스레드를 만들라고 한다
  • current-thread 런타임에서도 spawn_blocking 은 별도 스레드를 만든다

spawn_blocking 이 맞는 경우:

  • 동기 API 만 있는 라이브러리 호출(동기 DB 드라이버, 파일 시스템)
  • 언젠가 끝나는 짧은 blocking 작업
  • 요청 하나에 딸린 일이라 결과를 .await 로 받아야 하는 경우

thread::spawn 전용 스레드가 맞는 경우:

  • 프로세스가 살아 있는 동안 계속 실행되는 백그라운드 루프
  • 오래 실행돼 blocking 풀을 계속 차지하는 작업
  • 스레드 수와 수명을 직접 관리해야 하는 경우

두 목록은 실험이 아니라 tokio 문서의 설명을 기준으로 정리했다. 이 글에서 직접 확인한 것은 std::thread::sleep 을 spawn_blocking 으로 옮겼을 때 다른 태스크의 지연이 줄어든다는 것까지다.

마무리#

Future 는 poll 될 때마다 다음 .await 까지 진행하고 돌아오는 상태 머신이었다. tokio 는 이런 future 를 worker 몇 개로 번갈아 poll 하므로, poll 이 빨리 돌아와야 다른 태스크도 차례를 얻는다. 100ms 짜리 blocking 작업 4개가 worker 2개를 점유하자 10ms 타이머가 약 200ms 늦었고, spawn_blocking 으로 옮기자 blocking 이 없을 때와 같은 수 ms 로 돌아왔다.

시리즈 전체로 보면 소유권부터 Send 까지 대부분의 규칙은 컴파일러가 검사했다. unsafe 안의 전제와 async 의 “poll 은 blocking 하지 않는다"는 전제는 컴파일러가 보지 않으므로 코드를 쓰는 사람이 지켜야 한다.
