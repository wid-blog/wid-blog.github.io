unsafe 블록으로 감싸도 대여 검사와 타입 검사는 그대로 동작한다. 블록 안에서 같은 값에 가변 참조 두 개를 만들면 블록 밖과 똑같이 E0499 가 난다. unsafe 가 더 허용하는 것은 raw pointer 역참조처럼 컴파일러가 안전한지 확인할 수 없는 연산 몇 가지이고, 그 연산이 안전하다는 근거는 코드를 쓴 사람이 제시해야 한다. 성능 때문에 표준 라이브러리 밖의 자료구조를 직접 만들거나 그런 crate 를 받아 쓰는 백엔드 코드에서는, 이 경계가 어디인지 알아야 그 crate 의 코드를 읽을 수 있다. 그래서 unsafe 가 무엇을 허용하고, 그 안에서 무엇을 작성자가 책임지는지 정리하고 싶었다.

아래 예제는 모두 rustc 1.94.1, edition 2021 로 직접 컴파일하고 aarch64-apple-darwin(Apple M4 Pro, macOS 15.1)에서 실행했다. Miri 는 nightly toolchain 이 필요한데 이 머신에는 stable 만 있어 실행하지 않았고, 해당 절은 공식 문서를 인용했다.

raw pointer — 만들기는 safe, 역참조는 unsafe#

raw pointer 는 *const T 와 *mut T 두 가지다. Rust Book 은 참조와 다른 점으로 대여 규칙을 지키지 않아도 되고, 유효한 메모리를 가리킨다는 보장이 없고, null 일 수 있고, 자동 정리를 하지 않는다는 것을 든다. raw pointer 를 만드는 것은 safe 코드에서도 된다. 역참조만 unsafe 블록 안에서 할 수 있다.

fn main() {
    let mut count = 10;
    let ptr = &mut count as *mut i32;
    let nothing: *const i32 = std::ptr::null();
    let anywhere = 0x1234usize as *const i32;

    println!("nothing.is_null() = {}", nothing.is_null());
    println!("anywhere = {anywhere:?}");
    unsafe {
        *ptr += 1;
        println!("*ptr = {}", *ptr);
    }
    println!("count = {count}");
}

nothing.is_null() = true
anywhere = 0x1234
*ptr = 11
count = 11

null 포인터도, 아무 숫자를 주소로 바꾼 포인터도 만들고 출력하는 데까지는 문제가 없다. 주소를 값으로 다룰 뿐 그 주소를 읽지 않기 때문이다. 같은 역참조를 unsafe 밖에서 하면 컴파일러가 거부한다.

fn main() {
    let count = 10;
    let shared = &count as *const i32;
    println!("{}", *shared);
}

note 가 역참조에서 생길 수 있는 문제를 나열한다. null 이거나 이미 해제됐거나(dangling) 정렬이 맞지 않는 주소일 수 있고, 별칭 규칙을 어기거나 data race 를 일으킬 수 있다. 컴파일러는 raw pointer 에 대해 이것을 확인하지 못한다. 그래서 역참조를 unsafe 안으로 제한하고, 확인은 작성자에게 넘긴다.

unsafe 가 허용하는 다섯 가지#

Rust Book 은 safe Rust 에서 못 하고 unsafe Rust 에서만 할 수 있는 일을 다섯 가지로 든다. raw pointer 역참조, unsafe 함수·메서드 호출, static mut 변수 읽기·쓰기, unsafe trait 구현, union 필드 접근이다. The Rust Reference 의 목록에는 여기에 extern 블록 선언, unsafe 속성 적용, target_feature 함수 호출 같은 항목이 더 있다. 이 글은 FFI 를 다루지 않으므로 Book 의 다섯 가지만 본다. raw pointer 역참조는 앞 절에서 봤고, 나머지 네 가지를 한 프로그램에 모았다.

static mut REQUESTS: u64 = 0;

/// # Safety
/// `index` 는 `ids.len()` 보다 작아야 한다.
unsafe fn id_at(ids: &[u64], index: usize) -> u64 {
    // SAFETY: 호출자가 index < ids.len() 을 보장한다.
    unsafe { *ids.get_unchecked(index) }
}

#[repr(C)]
union Bits {
    float: f32,
    int: u32,
}

/// # Safety
/// 모든 바이트가 0 인 값이 이 타입의 올바른 값이어야 한다.
unsafe trait Zeroable {}

// SAFETY: u64 는 0 바이트 8개가 곧 0 이다.
unsafe impl Zeroable for u64 {}

fn zeroed<T: Zeroable>() -> T {
    // SAFETY: T: Zeroable 이 0 바이트 값이 올바르다고 약속한다.
    unsafe { std::mem::zeroed() }
}

fn main() {
    let ids = [7, 8, 9];
    let first = unsafe { id_at(&ids, 0) };

    unsafe {
        REQUESTS += 1;
    }
    let requests = unsafe { REQUESTS };

    let bits = Bits { float: 1.0 };
    let raw = unsafe { bits.int };

    let empty: u64 = zeroed();

    println!("first id = {first}, requests = {requests}");
    println!("1.0f32 bits = {raw:#x}, zeroed u64 = {empty}");
}

first id = 7, requests = 1
1.0f32 bits = 0x3f800000, zeroed u64 = 0

네 가지 모두 컴파일러가 확인할 수 없는 전제가 있다.

  • id_at 은 범위 검사 없이 원소를 읽는다. index 가 길이보다 작다는 전제는 호출하는 쪽이 지켜야 해서 함수 자체가 unsafe fn 이다
  • static mut 은 어느 스레드에서든 접근할 수 있어, 동시에 쓰면 data race 가 된다
  • union 은 여러 필드가 같은 바이트를 쓴다. 지금 든 바이트가 읽는 필드의 타입으로 올바른 값인지는 쓴 쪽만 안다. f32 1.0 을 쓰고 u32 로 읽으니 IEEE 754 비트 패턴 0x3f800000 이 나왔다
  • Zeroable 은 “0 바이트가 올바른 값” 이라는 약속을 구현하는 쪽에 요구한다. 그 약속을 믿고 zeroed 를 safe 함수로 둘 수 있다. &u64 나 NonZeroU32 처럼 0 이 올바른 값이 아닌 타입에 이 trait 를 구현하면 약속이 틀린다

/// # Safety 문서 절은 unsafe fn·unsafe trait 를 쓰는 쪽이 지켜야 할 조건을 적고, // SAFETY: 주석은 그 조건이 이 자리에서 왜 지켜지는지 적는다. Rust Book 은 둘 다 관례(idiomatic)라고 설명한다.

다섯 가지 밖의 검사는 unsafe 안에서도 그대로다. raw pointer 역참조로 unsafe 블록이 필요한 상황을 만들고, 같은 블록 안에서 count 에 가변 참조를 두 번 걸었다.

fn main() {
    let mut count = 10;
    let mut hits = 0;
    let hits_ptr = &mut hits as *mut i32;
    let first = &mut count;
    unsafe {
        *hits_ptr += 1;
        let second = &mut count;
        *first += 1;
        *second += 1;
    }
}

...

참조와 borrow 글에서 본 E0499 와 같다. Rust Book 도 unsafe 가 대여 검사나 다른 안전 검사를 끄지 않고, unsafe 코드 안에서 쓴 참조는 여전히 검사된다고 적는다.

정의되지 않은 동작 — 컴파일되고 실행돼도 틀린 코드#

unsafe 안의 약속을 어기면 정의되지 않은 동작(undefined behavior, UB)이 된다. The Rust Reference 는 UB 를 보이는 Rust 코드는 틀린 코드이고, 이는 unsafe 블록과 unsafe 함수 안의 코드에도 해당한다고 적는다. 대표 항목은 data race, 해제됐거나 정렬이 맞지 않는 주소 접근, 포인터 별칭 규칙 위반, bool 에 2 를 넣는 것 같은 잘못된 값 생성이다. 그리고 unsafe 는 UB 를 피할 책임이 프로그래머에게 있다는 뜻일 뿐, Rust 프로그램이 UB 를 일으켜서는 안 된다는 사실은 바뀌지 않는다고 덧붙인다.

UB 는 컴파일 에러로 드러나지 않는다. 아래 코드는 raw pointer 하나에서 가변 참조 두 개를 만든다. 대여 검사는 raw pointer 를 거친 참조를 추적하지 않아 그대로 컴파일된다.

fn main() {
    let mut count = 0;
    let ptr = &mut count as *mut i32;
    let first = unsafe { &mut *ptr };
    let second = unsafe { &mut *ptr };
    *first += 1;
    *second += 1;
    println!("count = {count}");
}

count = 2

debug 와 --release 빌드 모두 count = 2 를 출력했다. 그래도 이 코드는 틀렸다. first 가 살아 있는 동안 같은 값에 second 를 만들어 썼다. Reference 는 정확한 별칭 규칙이 아직 정해지지 않았다고 하면서 개요를 적는데, 그 개요의 가변 참조는 겹치지 않는다는 원칙을 어기므로 UB 로 봤다. 컴파일러는 이 규칙을 전제로 최적화하므로, 같은 코드가 다른 버전이나 다른 주변 코드에서 다른 결과를 낼 수 있다. 기대한 출력은 UB 가 없다는 근거가 되지 못한다.

safe API 로 감싸기 — split_at_mut#

unsafe 를 쓰는 코드도 외부 호출자에게는 safe 함수로 내보내는 경우가 많다. 표준 라이브러리의 slice::split_at_mut 이 그런 예다. 슬라이스 하나를 겹치지 않는 가변 슬라이스 두 개로 나눈다. 같은 일을 safe 코드로 쓰면 컴파일되지 않는다.

fn split_at_mut(values: &mut [i32], mid: usize) -> (&mut [i32], &mut [i32]) {
    let len = values.len();
    assert!(mid <= len);
    (&mut values[..mid], &mut values[mid..])
}

fn main() {
    let mut values = [1, 2, 3, 4];
    let (left, right) = split_at_mut(&mut values, 2);
    left[0] = 10;
    right[0] = 30;
}

두 범위 [..mid] 와 [mid..] 는 겹치지 않는다. 하지만 대여 검사는 같은 슬라이스를 두 번 가변으로 빌렸다는 것만 본다. Rust Book 도 이 함수는 safe Rust 만으로는 구현할 수 없다고 적는다. raw pointer 로 두 슬라이스를 직접 만들었다.

use std::slice;

fn split_at_mut(values: &mut [i32], mid: usize) -> (&mut [i32], &mut [i32]) {
    let len = values.len();
    let ptr = values.as_mut_ptr();
    assert!(mid <= len, "mid {mid} > len {len}");

    // SAFETY: mid <= len 이므로 [0, mid) 와 [mid, len) 은 values 안에 있고 겹치지 않는다.
    unsafe {
        (
            slice::from_raw_parts_mut(ptr, mid),
            slice::from_raw_parts_mut(ptr.add(mid), len - mid),
        )
    }
}

fn main() {
    let mut values = [1, 2, 3, 4];
    let (left, right) = split_at_mut(&mut values, 2);
    left[0] = 10;
    right[0] = 30;
    println!("{values:?}");

    let (_, _) = split_at_mut(&mut values, 5);
}

[10, 2, 30, 4]

thread 'main' (61634524) panicked at split.rs:6:5:
mid 5 > len 4

slice::from_raw_parts_mut 문서의 Safety 절이 나열한 주요 조건은 이렇다. 포인터가 null 이 아니고 정렬돼 있으며 len 개 원소만큼 읽고 쓸 수 있는 하나의 할당 안이어야 하고, 돌려받은 슬라이스가 살아 있는 동안 다른 포인터로 그 메모리에 접근하면 안 된다. ptr 은 values 에서 왔으니 앞의 조건은 values 가 이미 지키고 있다. 범위는 assert! 가, 겹치지 않음은 [0, mid) 와 [mid, len) 으로 나눈 계산이 보장한다.

mid 가 5 면 assert! 에서 panic 한다. panic 은 UB 가 아니다. 이 assert! 를 지워도 함수는 컴파일된다. 그러면 mid 가 길이보다 큰 호출을 막는 것이 없어 from_raw_parts_mut 의 조건이 깨지고, safe 코드가 safe 함수를 불렀을 뿐인데 UB 가 될 수 있다. 이 버전은 실행하지 않았다.

불변식과 책임 범위#

함수 시그니처에 unsafe 가 없으면, 어떤 인자로 불러도 UB 가 생기지 않는다는 약속이 된다. The Rust Reference 는 어떤 safe 호출자에게서도 UB 가 생기지 않는 unsafe 코드를 sound, safe 코드가 잘못 써서 UB 를 낼 수 있는 unsafe 코드를 unsound 라고 부른다. split_at_mut 에서 컴파일러가 확인하는 것은 인자와 반환값의 타입, 대여 규칙, 반환 참조의 라이프타임이다. 범위가 슬라이스 안이고 서로 겹치지 않는다는 조건은 컴파일러가 보지 않는다. 그 조건은 assert! 가 검사하고, SAFETY 주석이 근거를 적는다.

unsafe 가 기대는 조건이 인자가 아니라 struct 필드에 있으면 책임 범위가 넓어진다. Rustonomicon 의 Working with Unsafe 장은 Vec 의 용량(cap) 필드를 믿는 unsafe 코드를 예로 든다. 그 필드를 잘못 바꾸는 safe 메서드 하나만 추가해도 프로그램은 unsound 가 되고, 그런 unsafe 는 함수 하나가 아니라 모듈 전체에 영향을 준다고 적는다. 그리고 unsafe 코드의 범위를 제한하는 방법 중 일반적으로 확실한 것은 모듈 경계와 privacy 라고 정리한다. 필드를 private 으로 두면 그 필드를 바꿀 수 있는 코드가 정의한 모듈(과 그 하위 모듈) 안으로 한정되고, 검토할 범위도 거기로 좁혀진다.

Send 와 Sync 수동 구현#

Send 는 값을 다른 스레드로 옮겨도 된다는 표시, Sync 는 여러 스레드가 &T 를 함께 가져도 된다는 표시다. 둘 다 auto trait 라서, Rustonomicon 설명대로 필드가 모두 Send(또는 Sync)인 타입은 자동으로 Send(Sync)가 된다. raw pointer 는 안전 장치가 없어 Send 도 Sync 도 아니다. 그래서 raw pointer 필드 하나가 타입 전체를 스레드 사이로 못 넘기게 만든다. 힙 버퍼를 raw pointer 로 직접 관리하는 RawBuf 를 스레드로 넘겼다.

use std::thread;

struct RawBuf {
    ptr: *mut u64,
    len: usize,
}

impl RawBuf {
    fn new(len: usize) -> Self {
        let boxed = vec![0u64; len].into_boxed_slice();
        let ptr = Box::into_raw(boxed) as *mut u64;
        RawBuf { ptr, len }
    }

    fn set(&mut self, index: usize, value: u64) {
        assert!(index < self.len);
        // SAFETY: index < len 이고 ptr 은 len 칸짜리 할당을 가리킨다.
        unsafe { *self.ptr.add(index) = value }
    }

    fn sum(&self) -> u64 {
        // SAFETY: ptr 은 초기화된 len 칸을 가리키고, &self 동안 쓰기가 없다.
        unsafe { std::slice::from_raw_parts(self.ptr, self.len).iter().sum() }
    }
}

impl Drop for RawBuf {
    fn drop(&mut self) {
        // SAFETY: ptr 과 len 은 new 의 Box::into_raw 에서 온 값이고, 한 번만 해제한다.
        unsafe { drop(Box::from_raw(std::ptr::slice_from_raw_parts_mut(self.ptr, self.len))) }
    }
}

fn main() {
    let mut buf = RawBuf::new(4);
    buf.set(0, 5);
    let handle = thread::spawn(move || {
        buf.set(1, 7);
        buf.sum()
    });
    println!("sum = {}", handle.join().unwrap());
}

표준 라이브러리 경로는 줄였다. note 가 *mut u64 에서 RawBuf, 클로저, spawn 의 Send bound 까지 이어지는 경로를 보여 준다. 그런데 RawBuf 는 버퍼를 혼자 소유하고 포인터를 밖으로 내주지 않는다. Box<[u64]> 를 들고 있는 것과 같은 상황이고, Box<[u64]> 는 Send 다. 이 판단을 unsafe impl 로 적었다.

// SAFETY: RawBuf 는 버퍼를 혼자 소유하고, 포인터를 밖으로 내주지 않는다.
unsafe impl Send for RawBuf {}

sum = 12

나머지 코드는 그대로 두고 이 두 줄만 더했다. 컴파일러는 이 판단을 검증하지 않는다. 카운트를 동기화 없이 공유하는 Rc<i32> 를 필드로 가진 struct 에 같은 unsafe impl Send 를 붙여도 컴파일되고 실행된다.

use std::rc::Rc;

struct Shared {
    count: Rc<i32>,
}

unsafe impl Send for Shared {}

fn main() {
    let shared = Shared { count: Rc::new(1) };
    let handle = std::thread::spawn(move || {
        let shared = shared;
        *shared.count
    });
    println!("{}", handle.join().unwrap());
}

1

이 판단은 틀렸다. Rc 를 복제해 두 스레드가 카운트를 함께 바꾸면 data race 가 된다. Rustonomicon 은 Send 와 Sync 가 unsafe trait 라서 다른 unsafe 코드가 올바른 구현을 전제할 수 있고, 잘못 구현하면 UB 가 생길 수 있다고 적는다. RawBuf 의 sum 은 &self 로 읽기만 하므로 Sync 도 구현할 수 있어 보이지만, 필요하지 않은 약속은 하지 않았다.

Miri — 실행하며 UB 를 찾는 도구#

컴파일러가 놓친 UB 를 실행하며 찾는 대표적인 도구가 Miri 다. 앞서 적은 대로 Miri 는 실행하지 않았고, 아래는 Miri README 의 설명이다.

Miri README 는 Miri 를 cargo 프로젝트의 바이너리와 테스트를 실행하며 안전 조건을 지키지 않는 unsafe 코드를 찾는 UB 탐지 도구로 소개한다. 설치와 실행은 nightly toolchain 에서 한다.

rustup +nightly component add miri
cargo +nightly miri test
cargo +nightly miri run

README 가 예로 드는 탐지 대상은 범위 밖 접근과 해제 후 사용, 초기화되지 않은 데이터 사용, intrinsic 의 전제 위반, 정렬되지 않은 접근과 참조, bool 이 0·1 이 아닌 것 같은 타입 불변식 위반, data race 다. 참조의 별칭 규칙 위반은 Stacked Borrows, 또는 그 대안인 Tree Borrows 규칙으로 검사하는데 둘 다 실험적(experimental)이라고 표시한다. 앞 절의 first·second 코드는 별칭 규칙 위반이라 이 항목에 해당한다고 봤다. 그 코드에서 Miri 가 실제로 무엇을 출력하는지는 확인하지 않았다.

README 는 한계도 적는다. Miri 는 프로그램이 실행될 수 있는 여러 경로 중 하나를 시험하므로, 다른 경로에서만 생기는 버그는 놓친다. Rust 명세 위반을 모두 잡지는 않고, 코드가 sound 하다는 것도 보장하지 못한다. split_at_mut 에서 assert! 를 지운 버전을 Miri 로 돌려도, 테스트가 mid 를 길이보다 크게 넘기지 않으면 문제는 드러나지 않는다.

마무리#

unsafe 블록 안에서도 E0499 는 그대로 났다. unsafe 는 대여 검사를 끄지 않고, raw pointer 역참조처럼 Book 이 드는 다섯 가지 연산을 허용하는 대신 그 연산의 전제를 작성자가 지키게 한다. split_at_mut 에서는 assert! 와 범위 계산이, RawBuf 에서는 버퍼를 혼자 소유한다는 판단이 그 전제였다. 컴파일러는 그 전제가 맞는지 확인하지 않고, Miri 도 실행한 경로만 본다. 그래서 unsafe 코드는 그 전제를 SAFETY 주석으로 적고, 전제를 깰 수 있는 코드를 같은 모듈 안으로 한정한다. 다음 글에서는 async 의 Future 가 상태 머신으로 바뀌고, Pin 이 자기 자신을 가리키는 값을 어떻게 다루는지 본다.
