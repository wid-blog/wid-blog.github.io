Event Sourcing and CQRS

May 7, 2026 · 6 min read

microservices-architecture covered alignment axes and communication decisions, and distributed-transactions covered the decomposition and reassembly of single transactions. The next position in that decision chain is ES and CQRS — decisions about the form of the source of truth itself, and how views are derived from that truth.

ES and CQRS are separate patterns but connect into one abstraction. ES (Event Sourcing) keeps truth as a sequence of changes rather than state. The current state is derived. CQRS (Command Query Responsibility Segregation) separates distinct views from that truth. Changing the form of truth shifts the entire system design, so adoption must explicitly account for the cost.

Event Sourcing#

ES keeps the system’s truth as a sequence of changes rather than state.

A monolithic CRUD typically treats one thing as truth: the current value in a row. If the orders table reads PAID, the order is paid. Changes are overwritten by UPDATE, so how it reached that state is lost.

ES replaces that with a sequence of changes. OrderCreated, PaymentRequested, PaymentCompleted, OrderShipped — events accumulate append-only, and that sequence is the truth. “Is the current order paid?” is answered by replaying events from the beginning. State is derived.

This change looks small but shifts the entire premise of the system design.

  • An audit log follows naturally. Every change is already recorded as an event, so a separate audit infrastructure is unnecessary.
  • Time-travel debugging becomes possible. Stopping replay at a particular point reproduces the state at that point.
  • Adding a new view becomes free. A new projection over the event sequence yields a new read model.

The cost is built in. As events accumulate, replaying from scratch every time grows expensive. Snapshots are introduced for that reason — store a derived state at a point in time and replay only events after it. Schema changes are awkward as well. An event published years ago is still truth in the system, so its shape cannot be altered casually.

Kafka is often raised as an event store. The append-only log model aligns with ES. But Kafka’s retention policy typically deletes data after a window, while ES presumes permanent retention of every event — a conflict in defaults. Kafka mechanics are covered in kafka-fundamentals-kraft.

CQRS#

CQRS addresses the asymmetry of a single model.

Traditional CRUD handles both write and read with one model. In an order domain, a single Order carries validation, state change, search, and analytics. The setup is clean in a small system, but limitations show as the system grows. The write side wants business rules and transactional integrity; the read side wants fast queries and varied views. A single model rarely serves both well.

CQRS accepts the asymmetry. It separates the write model (Command side) from the read model (Query side). The write model is optimized for domain rules and consistency; the read model is optimized for representation and query efficiency. Both handle the same truth in different shapes.

The read model is not one but many. A search index, an analytics aggregate, a UI projection — each a read model derived from the same truth. New screen, new read model.

The decision point is when the read model is updated.

  • Synchronous update. The read model is updated in the same transaction as the write. Consistency is immediate but the write transaction bears more weight.
  • Asynchronous update. The write announces via an event and the read model updates in a separate flow. Eventual consistency. The most common pattern.
  • On-demand update. Derived at read time. Suits views with low query frequency.

Asynchronous updates introduce staleness — for a short window after a write, the read model may return the old value. Whether that staleness is acceptable to the business is the condition for adopting CQRS.

Combining ES and CQRS#

ES and CQRS are independent but pair naturally.

When ES treats truth as an event sequence, CQRS’s read model takes that sequence as input. As events are appended, projections consume them and update the read model. The event itself is read-side material, so the integration cost between the two patterns is small. A new read model means a new projection that replays events from the start.

The combination flows into Saga and Outbox from distributed-transactions. An ES event becomes a Saga trigger directly, and the “atomicity between DB write and event publication” that Outbox guarantees comes for free in ES — storing the event is storing the business data.

Trade-offs remain clear. Truth (events) and views (read models) live in different stores, so read and write consistency is not immediate. A user may not see the result of their action on screen right away. That point ties directly into UX decisions.

Adoption Criteria#

The alignment axes from microservices-architecture — domain boundary, data ownership, scale pattern, failure boundary — connect directly to ES/CQRS adoption.

  • When the domain demands audit/compliance as a core requirement ES fits naturally. Finance, insurance, healthcare.
  • When data ownership requires multiple read shapes for one domain CQRS follows. Search, analytics, and a real-time dashboard each demanding a different view of the same truth.
  • When the scale axis shows different load patterns for read and write CQRS read-model separation is natural. Different from a read replica — the models themselves differ.
  • When the failure axis disallows a read-side failure from blocking writes asynchronous read-model updates provide that isolation.

The point is not every system needs ES/CQRS. In a system where a single CRUD suffices, adopting ES adds the cost of derivation to every part of the system. The alignment axis sets the value of ES/CQRS, and whether that value justifies the cost is the condition for adoption.

Operational Cost#

Changing the form of truth is not a small decision. ES brings strong values — audit log, time travel, freedom in adding views — but the cost of receiving those values is distributed throughout the system.

  • Replay cost. Without snapshots, every replay starts from the beginning. With snapshots, the snapshots themselves carry operational weight.
  • Projection operations. Each read model’s update flow is managed separately. Reprocessing strategies are needed on failure.
  • Schema change difficulty. Past events cannot be altered freely, so versioning, upcasting, and weak/strong schema patterns are required as separate operational practice. This deserves its own post and is left for a follow-up.
  • Debugging abstraction. Tracing consistency between event sequences and projections is harder than reading a single state model.

If audit, compliance, time-travel debugging, or freedom in adding views are not core values of the system, plain CRUD is often the correct answer. ES/CQRS is the choice for when those values justify the cost.

When the pattern itself becomes the goal, the form of truth turns into post-hoc justification. The moment “event-driven architecture is good” becomes the reason for adoption, the system runs fine on the happy path while accumulating complexity without absorbing the value of ES — the same risk shape as “the cost of the wrong reassembly strategy” from distributed-transactions.

There are systems where changing the form of truth is worth it. When that value can be stated explicitly, adoption is a natural decision. When it cannot, holding off is the better call.
